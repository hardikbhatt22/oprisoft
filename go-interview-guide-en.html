Part 1 · Day 1 · Foundation

What Is Programming? Must Learn

Before learning Go, let's understand the absolute basics of programming. There is no code in this part — only concepts. Once you've read it, everything that follows will feel much easier.

1.1 What is a computer program?

A computer is a machine that cannot think for itself. It must be given step-by-step instructions. A list of such instructions is called a program.

Real-life example

Think of a recipe for making tea: (1) put water in a pot, (2) turn on the stove, (3) add tea and sugar, (4) add milk, (5) when it boils, strain it. The recipe is the "program", and the person following it is the "computer". If a step in the recipe is wrong (add milk first, then turn on the stove), the tea is ruined — in exactly the same way, a wrong step in a program produces a wrong result. A computer never "figures out what you meant" — it does exactly what you wrote, in exactly that order.

  • Programming = the activity of writing such instructions for a computer.
  • Programmer / Developer = the person who writes them (that's you, six days from now!).
  • Source code = the instructions a programmer writes in a text file. Code is just plain text — like something typed in Notepad — but written according to the rules of a particular language.

1.2 What is a programming language?

The hardware inside a computer understands only 0s and 1s (binary). Writing instructions in 0s and 1s is practically impossible for humans. So a middle path was invented: the programming language — a language humans can read and write, which can be converted into the computer's language.

Just as humans have many languages (English, Hindi, Gujarati), there are many programming languages — Go, Python, Java, C, and so on. Each has its own rules (grammar). We will learn Go, a simple and fast language created at Google in 2009.

  • Instruction = a command to do one small task. For example, "print Hello on the screen" or "add two numbers".
  • Syntax = the writing rules of the language — its grammar. Just as an English sentence needs a subject and a verb, every Go program must start with package. If the syntax is wrong, the computer cannot understand the code at all.
  • Logic = the correct order and reasoning of the instructions. Syntax can be perfect while the logic is wrong — like a grammatically correct sentence that says the wrong thing.

1.3 Input → Processing → Output

Almost every program does three things:

StepMeaningExample: a shop bill
InputInformation the program receives from outsideItem prices and quantities
ProcessingCalculation / work done on that informationSum of price × quantity, adding tax
OutputThe program's result — what becomes visibleThe total bill printed on screen

Output means the visible result a program produces. In most of our programs, the output will be text printed to the terminal (explained below).

1.4 Bugs and debugging

A bug is a mistake in a program that makes it produce wrong results, crash, or fail to start. Debugging is the process of finding and fixing bugs.

Example

You wrote a shop-bill program but accidentally subtracted the tax instead of adding it. The program runs — but the bill is wrong. That's a logic bug. Debugging means examining the numbers, finding which step is wrong, and fixing the code. Every programmer — including experienced ones — creates and fixes bugs every single day. A bug is not a failure; it's a normal part of the job.

1.5 Algorithms and flowcharts

An algorithm is a precise, ordered set of steps for solving a problem — a recipe without any programming language. First you think through the algorithm, then you write it in Go.

Example — the algorithm for "find the highest marks among three students":

  1. Treat the first student's marks as the "highest so far".
  2. If the second student's marks are higher, make those the "highest".
  3. Do the same for the third student.
  4. Whatever remains as "highest" at the end is the answer.

A flowchart is a picture of these steps — a map drawn with boxes and arrows. Decisions go in diamonds, actions in rectangles. Interviews rarely ask you to draw flowcharts, but the habit of "think through the steps first, write code second" is extremely valuable.

1.6 Compilers and interpreters

The source code you write must be converted into the computer's 0-and-1 language. There are two ways to do this conversion:

CompilerInterpreter
MethodConverts the whole program to machine language in advance, all at once, producing a runnable file (executable)Reads and executes the code line by line, while running
Translation analogyTranslating an entire book and printing it — reading it afterwards is fastA live interpreter standing next to a speaker — translating each sentence as it is spoken
SpeedFast to run (translation already done)Slower (translating every time)

Go is a compiled language — running go build produces a standalone .exe file that runs fast and needs nothing else installed to run. In interviews this is considered one of Go's biggest advantages.

Statically typed means: in Go, the type of every piece of data — whether it is a number or text — is decided and checked at compile time. If you accidentally try to add text to a number, Go reports the error before the program ever runs. (In contrast, dynamically typed languages catch this only while the program is running.) These two terms — compiled and statically typed — will be used throughout this guide, so make sure they're solid now.

1.7 Terminal, files, directories, and commands

  • File = a document stored on the computer — e.g. main.go (our code) or photo.jpg. Every file has a name and a type (extension). Go code files end in .go.
  • Directory (folder) = a container for files. Like drawers in a cupboard holding folders, a directory can contain files and other directories.
  • Terminal (command prompt) = the place where you talk to the computer by typing. Instead of clicking with a mouse, you type a command and press Enter. On Windows this is PowerShell or Command Prompt. VS Code has a built-in terminal too (menu: Terminal → New Terminal).
  • Command = an instruction typed into the terminal. For example, type go version and press Enter, and Go prints its version. As a programmer you'll use commands every day — nothing to fear, they're just "written instructions".
In short — Part 1 summary

Program = ordered instructions for a computer. Those instructions are written in a programming language (Go, for us) in text files. Go is compiled (converted to machine language in advance, hence fast) and statically typed (every piece of data has a fixed type, so many mistakes are caught early). We'll use the terminal to run commands and programs.

Install Go + Your First Program Must Learn

In this part we install Go and VS Code on Windows, then write and run your very first Go program — with every line explained.

2.1 Installing Go (Windows)

  1. Open go.dev/dl in your browser.
  2. Download the .msi file for "Microsoft Windows" — always take the latest stable version shown there (in October 2026 this will be a Go 1.2x release; whichever version is "featured" first is the right one).
  3. Double-click the downloaded .msi file → the installer opens → keep clicking Next → Finish. The installer sets up everything automatically (including PATH).
  4. After installing, close all open terminal windows and open a new one — old terminals don't know about the newly installed Go.

Verify the installation: go version

Press the Windows key, type PowerShell, open it, and type this command followed by Enter:

PowerShell
go version
go version go1.26.0 windows/amd64

If you see something like this (the version number may differ) — Go is installed. 🎉

Common installation errors and fixes
  • "go is not recognized as the name of a cmdlet..." — the terminal can't find Go. Fix: (1) close all terminals and open a new one. (2) If that fails, restart the computer. (3) Still failing? Reinstall Go and watch for the "Add to PATH" step in the installer.
  • Downloaded the wrong file — take the .msi (installer), not the .zip. The .msi configures everything for you.
  • 32-bit vs 64-bit — nearly all modern Windows machines are 64-bit (amd64); the default download is correct.

2.2 VS Code + the Go extension

  1. Download and install VS Code from code.visualstudio.com (Next → Next → Finish). VS Code is a free code editor — a programmer's Notepad, but much smarter.
  2. Open VS Code → click the square-blocks icon on the left (Extensions) → search for Go → the extension named "Go" (publisher: Go Team at Google) → Install.
  3. The first time you open a .go file, a popup appears at the bottom right asking to "Install All" (tools like gopls) — click Install All. These tools underline mistakes in your code and provide auto-complete.

2.3 Project folder and Go module

Let's create one folder for all our programs. Run these three commands in PowerShell, one after another:

PowerShell
mkdir go-practice
cd go-practice
go mod init go-practice

What each command does:

  • mkdir go-practice — "make directory": creates a new folder named go-practice.
  • cd go-practice — "change directory": moves the terminal inside that folder. Commands from now on run in this folder.
  • go mod init go-practice — makes this folder a Go module. A module is your project's identity. The command creates a small file named go.mod recording the module name and Go version. Every modern Go project starts with this command.
go: creating new go.mod: module go-practice

Now open this folder in VS Code: type code . and press Enter (type the dot too — it means "this folder").

2.4 Your first Go program

In VS Code, create a new file: main.go (File → New File → name it main.go → save inside the go-practice folder). Type the following — type it yourself:

main.go
package main

import "fmt"

func main() {
    fmt.Println("Hello, Go!")
}

Now open the terminal inside VS Code (Terminal → New Terminal) and run:

PowerShell
go run main.go
Hello, Go!

Congratulations — you wrote and ran your first program! Now let's understand every line, as if you had never seen code before:

Line-by-line explanation

  1. package main — every Go code file belongs to some package (group). The package named main is special: it tells Go "this is a runnable program, not a library." Every runnable Go program must have package main.
  2. (blank line) — just for readability; Go ignores blank lines.
  3. import "fmt" — Go ships with a large library of ready-made packages (the standard library). The fmt package (short for "format") contains tools for printing to the screen. import means "give me this package's tools to use." Just as you take utensils out of the cupboard before cooking, you import the packages you need before coding.
  4. func main() { — func declares a function — a named block of work (we'll study these in Part 3). The function named main is special: when the program starts, Go runs the main function first — it's the program's entrance (entry point). The { opens the function body.
  5. fmt.Println("Hello, Go!") — we use the Println tool from the fmt package ("Print line"). It prints the text in parentheses to the screen (terminal), then starts a new line. Text between quotation marks ("...") is called a string — simply "text" (more in Part 3).
  6. } — the main function's body ends here.

Common first-program mistakes
  • Writing fmt.println (lowercase p) — Go is case-sensitive. Println — capital P. Why capital? You'll find out in Part 5 (exported names).
  • Writing import "fmt" and then never using fmt — in Go, an unused import is an error, not a warning. (VS Code even removes unused imports automatically!)

  • Running go run without saving the file — the old code runs. Make Ctrl+S a habit.

3.1 Printing output and comments

What is it? Printing output = showing the program's result on the terminal. The three main tools in the fmt package:

main.go
package main

import "fmt"

func main() {
    // Println: prints and starts a new line
    fmt.Println("Shiksha Store")

    // Print: prints without a new line
    fmt.Print("Total: ")
    fmt.Print(250)
    fmt.Println() // empty Println = just a new line

    // Printf: prints according to a "format" — fill-in-the-blanks style
    fmt.Printf("Bill: %d rupees for %s\n", 250, "Ravi")
}
Shiksha Store
Total: 250
Bill: 250 rupees for Ravi

A comment is a note written inside the code that Go completely ignores — it exists only for humans (you and your team). Everything after // is a comment until the end of the line; everything between /* ... */ is a multi-line comment.

The Printf blanks (format verbs) — used in interviews and daily work alike:

3.2 Variables — boxes that hold information

What is it? A variable is a named box in the computer's memory that holds one value (a piece of information), and that value can be changed.

Why do we need it? A program must remember information while it works — a student's marks, an account balance, a customer's name. That information lives in variables.

Everyday example

Think of a school cupboard where every shelf has a student's name on it and the student's file inside. You can take the file out of the shelf labeled "Ravi" and put a new one in — the shelf (variable) stays the same, the contents (value) change. Go adds one extra rule: each shelf also has the kind of thing written on it — "only numbers go in this shelf". That is exactly static typing.

Two main ways to create a variable in Go:

variables.go
package main

import "fmt"

func main() {
    // Way 1: var name type = value  (the full form)
    var marks int = 85
    var name string = "Ravi"

    // Way 2: name := value  (short form — Go figures out the type)
    city := "Rajkot"   // inferred as string
    price := 99.50     // inferred as float64

    marks = 92 // change the value — plain =, not := (the box already exists)

    fmt.Println(name, "from", city)
    fmt.Println("Marks:", marks, "Price:", price)
}
Ravi from Rajkot
Marks: 92 Price: 99.5

Line-by-line

  1. var marks int = 85 — "create a box named marks, of type int (whole number), and put 85 in it." From now on, marks can never hold a string — the compiler will stop you.
  2. city := "Rajkot" — short declaration. := creates the box and fills it in one step; Go decides the type by looking at the right-hand value (type inference). This only works inside functions.
  3. marks = 92 — to change an existing variable's value, use plain =. Writing := again gives an error: "no new variables on left side of :=".
Common mistakes
  • Creating a variable and never using it — in Go, an unused local variable is a compile error ("declared and not used"). Interviews ask about this as a Go peculiarity.
  • Confusing := and = — use := to create a new box, = to change an existing one.
  • Using := outside a function (at package level) — only var works there.

Constants — values that never change

A value created with const can never be changed anywhere in the program. Use it for rule-like values — the GST rate, the value of π, the shop's name:

const.go
const gstRate = 0.18
const storeName string = "Shiksha Store"

// gstRate = 0.20  // ← writing this gives a compile error: cannot assign to gstRate

Benefit: an important value can't be changed by accident, and readers of the code know it is "permanent".

Numbers and arithmetic

bill.go — a shop bill
package main

import "fmt"

func main() {
    price := 120         // int
    qty := 3             // int
    total := price * qty // 360

    fmt.Println("Subtotal:", total)
    fmt.Println("Add:", 10+3, "Subtract:", 10-3)
    fmt.Println("Divide:", 10/3)   // 3  ← int ÷ int = int! The decimal part is cut off
    fmt.Println("Remainder:", 10%3) // 1 ← remainder (modulo)
    fmt.Println("Float divide:", 10.0/3.0) // 3.3333...
}
Subtotal: 360
Add: 13 Subtract: 7
Divide: 3
Remainder: 1

Two famous mistakes
  • Integer division: 10/3 = 3 (not 3.33!) — when both sides are ints, the answer is an int too; the decimal part is thrown away. If you need decimals, use floats.
  • % (remainder) — the most-used tool for checking even/odd: n%2 == 0 means even. (The == comparison is explained in 3.4 below.)

Type conversion — changing a value's type

Go never converts types automatically (many other languages do — Go deliberately doesn't, to prevent hidden bugs). To add an int to a float, you must convert explicitly — by using the type's name like a function:

convert.go
qty := 3                      // int
price := 99.50                // float64
total := float64(qty) * price // converting int → float64 is required

// total := qty * price  ← error: mismatched types int and float64

marks := 427
subjects := 5
avg := float64(marks) / float64(subjects) // 85.4 (float division)
fmt.Printf("Total: %.2f, Average: %.1f\n", total, avg)
Total: 298.50, Average: 85.4

To convert between strings and numbers, use the strconv package: strconv.Itoa(42) → "42" (int-to-ASCII), and strconv.Atoi("42") → 42, nil (it returns two values — explained in 3.10). Not string(42) — that doesn't give "42"; it gives the character whose code is 42, '*' — a famous trap!

Taking user input

input.go
package main

import "fmt"

func main() {
    var name string
    var marks int

    fmt.Print("Enter name: ")
    fmt.Scanln(&name) // & = "put the answer at this variable's address" (depth in 3.11, pointers)

    fmt.Print("Enter marks: ")
    fmt.Scanln(&marks)

    fmt.Printf("%s scored %d marks\n", name, marks)
}
Enter name: Ravi
Enter marks: 85
Ravi scored 85 marks

Scanln reads the user's keyboard input and puts it into the variable. The full meaning of & comes with pointers (3.11) — for now remember that the & before the variable in Scanln is mandatory; without it the value never arrives.

3.1–3.4 — Interview Questions

Both create variables. var works anywhere and lets you write the type; := is the short form — it infers the type but only works inside functions.
var declares a variable with an optional explicit type and works at both package and function level. := is short variable declaration: it declares and initializes in one step with type inference, but it only works inside functions. In both cases the type is fixed at compile time.

3.5 Decisions: if, else, and switch

What is it? So far our programs ran straight from top to bottom. if teaches a program to make decisions: "if this condition is true, do this; otherwise, do that."

Example

A teacher checks a result: if marks are above 33 → write "Pass", otherwise → write "Fail". That's exactly if/else.

grade.go — a student's grade
package main

import "fmt"

func main() {
    marks := 78

    if marks >= 80 {
        fmt.Println("Grade A")
    } else if marks >= 60 {
        fmt.Println("Grade B")
    } else if marks >= 33 {
        fmt.Println("Grade C - Pass")
    } else {
        fmt.Println("Fail")
    }
}
Grade B

Line-by-line

  1. if marks >= 80 { — checks the condition. In Go, you do not write parentheses ( ) around the condition (unlike other languages!), but the { } braces are mandatory — even for a single line.
  2. Is 78 ≥ 80? No → the next else if is checked: 78 ≥ 60? Yes → "Grade B" prints, and the rest of the chain is skipped. Top to bottom, only the first true condition runs.
  3. Change the input: marks := 95 → "Grade A"; marks := 20 → "Fail".

A Go specialty — if with a statement: you can do one small task before the condition. This is used heavily in Go error handling (you'll see it in 3.10):

if-statement.go
if total := price * qty; total > 1000 {
    fmt.Println("Free delivery!") // total lives only inside this if block
}

switch — choosing one of many options

When one value must be compared against many options, switch reads more cleanly than a long if/else chain:

order.go — restaurant orders
day := "Sunday"

switch day {
case "Saturday", "Sunday":        // one case can list several values
    fmt.Println("Weekend special menu")
case "Monday":

In other languages you must write break at the end of each case, or execution "falls through" to the next case. In Go, break is automatic — only the matched case runs. To fall through deliberately, you must write the fallthrough keyword (rarely used).

3.6 The for loop — repeating work

What is it? A loop makes the computer repeat the same task. To print 500 students' marks you don't write 500 lines — you write one loop.

Interview favourite fact: Go has exactly one loop keyword — for. The while and do-while of other languages are all just forms of for in Go.

loops.go — the four forms of for
package main

import "fmt"

func main() {
    // Form 1: classic — init; condition; change
    for i := 1; i <= 5; i++ {
        fmt.Println("Table:", 7*i)
    }

    // Form 2: condition only (like a while)
    balance := 100
    for balance > 0 {
        balance -= 40
    }
    fmt.Println("Final balance:", balance)

    // Form 3: infinite loop (used in servers; exited with break)
    count := 0
    for {
        count++
        if count == 3 {
            break // break out of the loop
        }
    }
    fmt.Println("Count:", count)

    // Form 4: range — walking over a collection (depth in 3.8 with slices)
    for i := range 3 { // 0, 1, 2  (range over int, Go 1.22+)
        fmt.Println("Step", i)
    }
}

Line-by-line (Form 1)

  1. i := 1 — creates the counter, starting at 1. (Naming the loop variable i is an old tradition.)
  2. i <= 5 — checked before every round; the loop ends as soon as it becomes false.
  3. i++ — after each round, adds 1 to i. (i++ = i = i + 1.)
  4. So the body runs 5 times: i = 1, 2, 3, 4, 5. At i = 6 the condition is false → done.

break = immediately exit the loop. continue = skip this round and jump to the next one:

Common mistakes
  • Writing a condition that can never become false (i > 0; i++) — an infinite loop; the program never stops. Stop it with Ctrl+C in the terminal.
  • Writing i < 5 instead of i <= 5 — one round too few (the off-by-one error — the world's most famous bug!).

3.7 Functions — named pieces of work

What is it? A function is a named block of code that can take input (parameters) and send back a result (return value). Write it once, use it as many times as you like.

Why do we need it? (1) If the same calculation is needed in 10 places, you don't copy code — you call a function. (2) Big programs get split into small, understandable pieces. (3) Fixing a bug means fixing one place.

Example

In a restaurant you order a "masala dosa" (function call + parameter) → the kitchen does the whole process (function body — you don't need to know it) → a finished dosa comes back (return value). You get work done by name alone, without knowing the recipe.

functions.go — a shop bill
package main

import "fmt"

// addGST: one parameter (amount), one return value (float64)
func addGST(amount float64) float64 {
    return amount * 1.18
}

// makeBill: two parameters, two return values! (a Go specialty)
func makeBill(price float64, qty int) (float64, float64) {
    subtotal := price * float64(qty)
    total := addGST(subtotal) // calling one function from another
    return subtotal, total
}

func main() {
    sub, total := makeBill(100, 3)
    fmt.Printf("Subtotal: %.2f, With GST: %.2f\n", sub, total)
}
Subtotal: 300.00, With GST: 354.00

Line-by-line

  1. func addGST(amount float64) float64 { — read it as: "a function named addGST, which takes a float64 input named amount, and gives back a float64." The float64 after the parentheses is the return type.
  2. return amount * 1.18 — computes and "sends back" the answer. As soon as return runs, the function is finished.
  3. func makeBill(...) (float64, float64) — two return values! Multiple return types go in parentheses. This is very common in Go — especially the "(result, error)" pair (see 3.10).
  4. sub, total := makeBill(100, 3) — both answers are caught in two variables. If you don't need one, replace it with _ (the blank identifier): _, total := makeBill(100, 3). In Go, "take it and throw it away" must be written explicitly.
Scope — where a variable "lives"

A variable created inside a function is visible only in that function (local). One created inside a { } block is visible only in that block. Outer scopes are visible from inside; inner ones are not visible from outside. That's why makeBill's subtotal can't be used in main — it only gets out via return.

Common mistakes
  • Declaring a return type but not returning on every path — compile error: "missing return".
  • Catching only one of two return values — error. Catch both or use _.
  • Shortening repeated parameter types is allowed: func add(a, b int) = both are int.

3.8 Arrays, Slices, and Maps — lists of data Must Learn

So far every variable held a single value. The real world is full of lists — 60 students' marks, 200 product prices. Go has three structures for this: array, slice, and map. Interviews probe all three in depth — give this section serious time.

Array — a fixed-length list

Example

An egg carton with 10 slots. Exactly 10 — it can't grow or shrink. Every slot has a position (index), and counting starts from 0 — the first slot is index 0, the second index 1... Counting from zero is one of programming's most important habits.

array.go
var marks [5]int                  // an array of 5 ints — all start at zero value 0
marks[0] = 85                     // 85 in the first slot
marks[1] = 90
fmt.Println(marks)                // [85 90 0 0 0]
fmt.Println(len(marks))           // 5 — len() = length

days := [3]string{"Mon", "Tue", "Wed"} // filling it at creation
fmt.Println(days[2])              // Wed (index 2 = the third!)

An array's length is part of its type: [5]int and [6]int are different types! The length can never change. Because of this rigidity, plain arrays are rare in Go — slices are used instead.

Slice — a growable list (Go's everyday tool)

What is it? A slice is a flexible list built on top of an array — you can append elements, and the length is not part of the type. It's written like an array but without a number in the brackets: []int.

slice.go — students' marks
package main

import "fmt"

func main() {
    marks := []int{85, 90, 70}          // a slice — brackets with no number
    fmt.Println(len(marks), cap(marks)) // 3 3

    marks = append(marks, 95)           // adding: append! catching the result is mandatory
    marks = append(marks, 60, 88)       // several at once is fine too
    fmt.Println(marks)                  // [85 90 70 95 60 88]
    fmt.Println(len(marks), cap(marks)) // 6 6 (cap can often be more than 6)

    // Slicing: a piece of the list — marks[start:end]  (end NOT included!)
    top3 := marks[0:3]                  // indexes 0,1,2 → [85 90 70]
    fmt.Println(top3)

    // walking with range: you get index and value
    total := 0
    for i, m := range marks {
        fmt.Printf("Student %d: %d\n", i+1, m)
        total += m
    }
    fmt.Println("Average:", total/len(marks))
}

len vs cap — a beloved interview question

Inside, a slice is really three things: (1) a pointer to the underlying array, (2) length — how many elements are in it right now, (3) capacity — how much total room the underlying array has.

Example

A hall with 50 chairs (capacity = 50) currently seating 30 guests (length = 30). If 20 more arrive, there are chairs ready. What about guest number 51? append rents a bigger hall (allocates a larger array, usually about double), moves all the guests there, and uses the new hall. That's exactly why catching append's return value is mandatory — the new hall may not be at the old address!

Famous slice mistakes
  • Writing append(marks, 95) without catching the result — a compile error or a lost element. Always marks = append(marks, 95).
  • Assigning by index into an empty slice: var s []int; s[0] = 5 → runtime panic: index out of range. To add to an empty slice, only append works.
  • In marks[1:3], the end index is not included — you get indexes 1 and 2, not 3.
  • Two slices can view the same underlying array — changing one shows up in the other! (Set top3[0] = 1 and marks[0] becomes 1 too.) A tricky interview question.

Map — a key→value collection

What is it? In a map, you store and look up values by a key of your choosing instead of a position (0,1,2...). Think of your phone's contact book: name (key) → number (value). Give the name, get the number instantly — no searching through the whole list.

map.go — product inventory
package main

import "fmt"

func main() {
    // create with make() — or with the literal form below
    stock := map[string]int{   // key: string (product), value: int (quantity)
        "pen":      120,
        "notebook": 45,
    }

    stock["eraser"] = 200        // adding / changing — same syntax
    fmt.Println(stock["pen"])    // 120 — looking up by key

    delete(stock, "notebook")    // removing
    fmt.Println(len(stock))      // 2

    // ★ "comma ok" — the correct way to check whether a key exists
    qty, ok := stock["pencil"]
    if ok {
        fmt.Println("Pencil stock:", qty)
    } else {
        fmt.Println("Pencil not in inventory") // this prints
    }

    // walking over a map
    for product, qty := range stock {
        fmt.Println(product, "=", qty)
    }
}

Famous map mistakes — all three come up in interviews
  • Asking for a missing key is not an error! stock["pencil"] silently returns the zero value (0). Is the stock 0, or does the product not exist? To tell the difference you must use the comma ok form (qty, ok := stock["pencil"]).
  • Writing to a nil map = panic: after var m map[string]int (the zero value is nil), m["a"] = 1 → panic: assignment to entry in nil map. Initialize with make(map[string]int) first.
  • Map order is random — range visits keys in a different order every run. Go deliberately shuffles it so no one relies on ordering!

3.9 Strings, bytes, and runes Important if time permits

What's inside a string? Computers store numbers, not characters. Every character has been assigned a number ('A' = 65, 'B' = 66 — the Unicode system). A Go string is an immutable sequence of bytes.

3.10 Error handling — first introduction Must Learn

What is it? Many operations can fail: a file isn't found, "abc" is asked to become a number, you divide by zero. In Go, such a failure is returned from the function as a value called an error — it is never hidden.

Go's approach differs from other languages (a big interview topic): many languages "throw exceptions" that get caught somewhere far away. Go says: an error is just an ordinary value — the function returns it as the last return value, and the caller checks it immediately.

errors.go — reading a payment amount
package main

import (
    "errors"
    "fmt"
    "strconv"
)

// our own function that returns an error
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("cannot divide by zero")
    }
    return a / b, nil // success → nil ("nothing") in the error slot
}

func main() {
    // a standard-library example: string → int
    amount, err := strconv.Atoi("450")
    if err != nil {                    // ★ Go's three most famous lines
        fmt.Println("Invalid amount:", err)
        return
    }
    fmt.Println("Payment amount:", amount)

    result, err := divide(100, 0)
    if err != nil {
        fmt.Println("Error:", err)
        return
    }
    fmt.Println("Result:", result)
}
Payment amount: 450
Error: cannot divide by zero

Line-by-line

  1. (float64, error) — two return values: the answer + an error. The error always comes last — a Go convention.
  2. errors.New("...") — creates a new error value with a message.
  3. return a / b, nil — nil means "empty — no error". The sign of success.
  4. if err != nil { ... return } — "is the error non-empty? Then handle it and go no further." You will write this pattern thousands of times in Go. It may feel repetitive, but every failure stays visible — that's Go's design philosophy.

3.11 Pointers — a memory address Must Learn

What is it? Every variable lives somewhere in the computer's memory, and that place has an address. A pointer is a variable that holds not a value, but the address of another variable.

Why do we need it? When you give a variable to a function in Go, a copy is passed — not the original. If the function changes the copy, the original stays untouched. To let a function change the original, you must give it the address instead of a copy — and that's a pointer.

Example

Give someone a photocopy of your house documents — whatever they scribble on the copy, your original stays safe. But give them your home address, and they can come over and make real changes. Copy = normal parameter; address = pointer.

Only two symbols to remember:

  • &x — "give me the address of x" (address-of)
  • *p — "go to the address in p and fetch/store the value" (dereference). In a type, *int = "a pointer holding the address of an int".
pointer.go — depositing money in a bank
package main

import "fmt"

// takes a copy — the original balance will NOT change!
func depositBroken(balance float64, amount float64) {
    balance += amount // only the copy changed
}

// *float64 = takes the balance's address — the original WILL change ✓
func deposit(balance *float64, amount float64) {
    *balance += amount // go to the address and change the original value
}

func main() {
    balance := 1000.0

    depositBroken(balance, 500)
    fmt.Println("After broken deposit:", balance) // 1000 — unchanged!

    deposit(&balance, 500)                    // & = sent the address
    fmt.Println("After real deposit:", balance)   // 1500 ✓
}
After broken deposit: 1000
After real deposit: 1500

Line-by-line

  1. depositBroken(balance, 500) — Go handed the function a copy of 1000. The function added 500 to the copy; when the function ended, the copy was discarded. The original is untouched. (This is pass by value — and in Go, everything is passed this way.)
  2. deposit(&balance, 500) — &balance = the address of balance. Now the function has the original's location, not a copy.
  3. *balance += amount — "add to whatever is at this address." The original changed.
  4. Remember fmt.Scanln(&name) from 3.3? Now it makes sense: Scanln needs the address of name so it can put your input there!
Pointer mistakes
  • nil pointer dereference — a pointer's zero value is nil (the address of nowhere). var p *int; fmt.Println(*p) → panic! Check first: if p != nil.
  • Go has no pointer arithmetic (no p+1 as in C) — this makes Go safer. Interview point!

3.12 Structs — a bundle of related data Must Learn

What is it? One student's data = name + roll number + marks. Instead of three loose variables, a struct binds them under one name — your own custom type.

Example

A school admission form — it has fixed printed boxes: name, age, class. The blank form (template) = the struct type. Each student's filled-in form = one value of that type. The boxes are called fields.

3.13 Methods — a struct's own functions Must Learn

What is it? A method is a function attached to a specific type. "Give an Employee a raise", "withdraw from a BankAccount" — these jobs belong to that type. Writing a receiver in parentheses before the function name turns the function into that type's method.

methods.go — a bank account
package main

import "fmt"

type Account struct {
    Owner   string
    Balance float64
}

// Value receiver (a Account) — gets a copy: for reading only
func (a Account) Show() {
    fmt.Printf("%s has %.2f\n", a.Owner, a.Balance)
}

// Pointer receiver (a *Account) — gets the address: for modifying ✓
func (a *Account) Deposit(amount float64) {
    a.Balance += amount
}

func main() {
    acc := Account{Owner: "Ravi", Balance: 1000}
    acc.Deposit(500)  // calling a method: value.MethodName()
    acc.Show()
}
Ravi has 1500.00

Value receiver vs pointer receiver — a guaranteed interview question:

  • func (a Account) Show() — value receiver: the method gets a copy of the struct. Fine for reading; changes affect only the copy.
  • func (a *Account) Deposit() — pointer receiver: the method gets the address. The original struct changes. Also used to avoid copying large structs.
  • Rule: if any method of a type needs a pointer receiver, give all its methods pointer receivers — for consistency.

3.14 Interfaces — a promise of "what it can do" Must Learn

What is it? An interface is not a struct-like type — it is a list of methods: "any type that has these methods counts as this interface." An interface says what must be done, not how.

Why do we need it? A payment example: a shop accepts payment by UPI, by card, in cash — any way at all. The shop doesn't care about the method; it just needs "Pay to happen". With an interface we can write: "give me anything that can Pay" — and one piece of code works with every payment method.

Example

Think of a driving licence. The licensing office doesn't ask which brand of car you'll drive — only "can you drive?" The licence = the interface (a promise of "can drive"). Whether it's a Maruti or a Tata (different structs), a licence holder can drive both. A job ad saying "driver wanted" asks for the ability, not one specific car.

interface.go — payment processing
package main

import "fmt"

// The interface: "a Payer is anything that has a Pay(amount) method"
type Payer interface {
    Pay(amount float64) string
}

type UPI struct{ VPA string }
type Card struct{ Number string }

// UPI has Pay → UPI automatically became a Payer! (no declaration anywhere)
func (u UPI) Pay(amount float64) string {
    return fmt.Sprintf("Paid %.2f via UPI %s", amount, u.VPA)
}

func (c Card) Pay(amount float64) string {
    return fmt.Sprintf("Paid %.2f via card ending %s", amount, c.Number)
}

// this function doesn't care about the method — any Payer works
func checkout(p Payer, bill float64) {
    fmt.Println(p.Pay(bill))
}

func main() {
    checkout(UPI{VPA: "ravi@okbank"}, 450)
    checkout(Card{Number: "4242"}, 1200)
}
Paid 450.00 via UPI ravi@okbank
Paid 1200.00 via card ending 4242

The most important point — implicit implementation

Look carefully: UPI never declared anywhere that "I am a Payer." It simply has a Pay method — and Go automatically accepted that UPI is a Payer. This is called implicit interface implementation — Go's most celebrated feature and a guaranteed interview question. (In languages like Java you must explicitly write "implements Payer".) The benefit: an interface can be created after the fact — you can define a new interface for old types without touching them.

The standard library's most famous interface — error! It is simply: type error interface { Error() string }. And the empty interface any (= interface{}) — zero methods, so every type satisfies it — is used for "a value of any type".

func reverse(s string) string {
    r := []rune(s)                    // runes — so non-English text doesn't break
    for i, j := 0, len(r)-1; i < j; i, j = i+1, j-1 {

    return string(r)

func calc(a, b float64, op string) (float64, error) {

    case "+": return a + b, nil
    case "-": return a - b, nil
    case "*": return a * b, nil
    case "/":

        return fmt.Errorf("insufficient funds: have %.2f, want %.2f",

}

5.1 Packages, modules, and exported names Must Learn

A package is a group of related .go files — one folder = one package. A module is the whole project — a bundle of packages plus the go.mod file (its name and dependency list). Need an external library? Fetch it with go get and it's recorded in go.mod.

Example

Module = the whole shop; packages = the shop's departments (billing department, inventory department). Each department has some items for customers (in the showcase) and some only for staff (behind the counter).

Exported vs unexported — Go's most elegant rule: if a name's first letter is capital, it can be used from outside the package (exported — the showcase); if it's lowercase, it's only usable inside the package (unexported — behind the counter). There are no public/private keywords — just letter case! Now you know why fmt.Println has a capital P — it's exported from the fmt package for us to use.

billing/gst.go — your own package
package billing

const gstRate = 0.18          // lowercase g → only inside the billing package

// Capital T → usable across the whole module
func TotalWithGST(amount float64) float64 {
    return amount * (1 + gstRate)
}
// in main.go: import "go-practice/billing" → billing.TotalWithGST(500)

5.2 defer — "do this on the way out" Must Learn

A statement marked with defer runs when the function finishes — no matter what happens in between (an error, an early return). Perfect for cleanup: closing a file, releasing a lock, closing a connection.

Example

The moment you enter the shop, you decide: "I'll switch off the lights on my way out." Then whatever happens inside — customers arrive, stock runs out, you leave early — the lights get switched off at the exit. Open a resource and write its deferred close on the very next line — then it can never be forgotten.

defer.go
func main() {
    fmt.Println("Shop open")
    defer fmt.Println("Lights off")   // registered — will run last
    defer fmt.Println("Door locked")  // a second defer

    fmt.Println("Serving customers")
}
Shop open
Serving customers
Door locked
Lights off

Two interview points: (1) Multiple defers run in reverse order (LIFO — last registered runs first) — see above. (2) A defer's arguments are evaluated at the defer line itself, not at function exit — i := 1; defer fmt.Println(i); i = 99 prints 1, not 99!

5.3 panic and recover Important if time permits

A panic is a program emergency — "continuing is simply impossible." Index out of range, writing to a nil map, or calling panic("...") yourself. When a panic occurs, the function stops, all defers run, and the panic spreads upward — if nothing stops it, the program crashes and prints a stack trace.

Recover is the tool that catches a panic — and it works only inside a deferred function. Web servers use this so that one panicking request doesn't bring down the whole server.

recover.go
func safeProcess(orderID int) {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("Order", orderID, "failed, server still alive:", r)
        }
    }()
    if orderID == 0 {
        panic("invalid order id")
    }
    fmt.Println("Processed order", orderID)
}

func main() {
    safeProcess(7)
    safeProcess(0)   // will panic — but gets caught
    safeProcess(9)   // the program is still running!
}
Processed order 7
Order 0 failed, server still alive: invalid order id
Processed order 9
Interview sound-bite — error vs panic

"Errors are for expected failures — a missing file, invalid input — and are returned as values. Panic is for unrecoverable programmer errors. Idiomatic Go returns errors; it almost never panics in libraries."

5.4 Type assertion and type switch Important if time permits

When you need to know "what type is really inside?" an interface value:

assert.go
var data any = "hello"            // any = the empty interface — any value at all

s, ok := data.(string)            // type assertion — always use the comma ok form!
fmt.Println(s, ok)                // hello true

n, ok := data.(int)
fmt.Println(n, ok)                // 0 false  (no panic — because we asked the ok way)

switch v := data.(type) {         // type switch — against several types

    fmt.Println("string of length", len(v))

    fmt.Println("number", v)

    fmt.Println("something else")

Danger: s := data.(int) — an assertion without ok panics if it's wrong. Always use the comma-ok form.

5.5 Nil and nil interfaces Advanced — read later

nil means "nothing" — the zero value of pointers, slices, maps, channels, interfaces, and functions. Each behaves differently when nil: appending to a nil slice works ✓, writing to a nil map panics ✗, dereferencing a nil pointer panics ✗.

The famous trap (asked in senior interviews): an interface value has two parts — (type, value). Put a "nil pointer" inside an interface and the interface becomes non-nil (the type part is filled!) — so err != nil comes out true even though the pointer inside is nil. Rarely asked at beginner level — for now just remember: "when returning an error, return a literal nil, never a nil typed pointer."

5.6 Generics — a short introduction Advanced — read later

Since Go 1.18, you can write a function "for any type" — with a type parameter [T ...]. For example, one function that sums both int and float64 slices:

generics.go
func Sum[T int | float64](values []T) T {
    var total T                    // T's zero value
    for _, v := range values {
        total += v
    }
    return total
}
// Sum([]int{1, 2, 3}) → 6    Sum([]float64{1.5, 2.5}) → 4.0

For the 6-day plan, this sentence is enough: "Go supports generics since 1.18 via type parameters; they remove the need to duplicate functions for each type or fall back to any." Depth comes after the interview.

5.7 Idiomatic Go — naming and etiquette Important if time permits

  • Names in camelCase: totalAmount, userID (not snake_case: total_amount ✗).
  • Short names are fine where the meaning is clear: i in loops, a as a receiver, err for errors.
  • Interface names often end in "-er": Reader, Writer, Payer — "the thing that does this".
  • Error strings start lowercase, no trailing period: errors.New("file not found").
  • Never think about formatting — gofmt decides. "Gofmt's style is no one's favourite, yet gofmt is everyone's favourite" — a Go proverb worth quoting in an interview!

Concurrency — From Zero Must Learn

Concurrency is Go's most famous feature — it is almost guaranteed to come up in a Go interview. We'll start from "what is a thread" and build up.

6.1 The basic vocabulary — process, thread, concurrency, parallelism

Sequential execution: every program so far did one thing at a time — line 1, then line 2, then line 3. One task finishes, then the next begins. For most programs this is plenty.

But here's the problem: suppose your program must send notifications to 100 customers, and each notification takes 1 second (waiting on the network). Sequentially = 100 seconds! Most of that time the program is just waiting — the CPU sits idle. Why not do other work during the wait? That question is where concurrency begins.

"Concurrency is about dealing with many things at once; parallelism is about doing many things at once." — Concurrency is a matter of design; parallelism is a matter of execution. Go lets you write concurrency; given cores, the runtime also runs it in parallel.

6.2 Goroutines — Go's featherweight workers

What is it? A goroutine is an extremely lightweight "thread" managed by the Go runtime. Put go in front of any function call — done, that function now runs separately, concurrently.

Why is it special? An OS thread needs ~1–8 MB of memory; a goroutine starts at ~2 KB. Thousands of OS threads strain a machine; millions of goroutines are routine. The Go runtime keeps scheduling goroutines onto a few OS threads — you do nothing. This is Go's superpower.

goroutine.go — the wrong way (on purpose!)
package main

import "fmt"

func sendNotification(customer string) {
    fmt.Println("Notified", customer)
}

func main() {
    go sendNotification("Ravi")   // run in a new goroutine
    go sendNotification("Mina")
    fmt.Println("Main done")
    // "Notified..." may never print at all! Why? ↓
}
Main done
The first and biggest mistake

When the main function ends, the whole program ends — running goroutines are not waited for; they are cut off mid-flight. In the program above, main finished so fast the notifications were never sent. The fix: wait for the goroutines — the correct tool is sync.WaitGroup (below). (Waiting with time.Sleep is a hack, not a fix — never say that in an interview!)

sync.WaitGroup — "wait until everyone's done"

Example

A teacher assigns cleanup jobs to 30 students and writes "remaining: 30" on the board. Each student finishes and decrements the count. Only when "remaining: 0" does the teacher leave the classroom. WaitGroup = that counter: Add(1) = job registered, Done() = one finished, Wait() = stand here until zero.

waitgroup.go — the right way
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    customers := []string{"Ravi", "Mina", "Amit"}

    for _, c := range customers {
        wg.Add(1)                   // register BEFORE starting the goroutine
        go func(name string) {
            defer wg.Done()         // decrement when finished — defer makes it certain
            fmt.Println("Notified", name)
        }(c)
    }

    wg.Wait()                       // block until the counter reaches 0
    fmt.Println("All notifications sent")
}
Notified Mina
Notified Ravi
Notified Amit
All notifications sent

Note: the order of the three "Notified" lines can differ every run — goroutines run concurrently with no ordering guarantee. The last line is always last — Wait() guarantees it. (Older Go required passing the loop variable as a parameter — the (c) above — because iterations shared one variable; since Go 1.22 each iteration gets a fresh variable, but interviews still ask about this old trap!)

6.3 Channels — pipes between goroutines

What is it? A safe pipe for sending data between two goroutines. Send from one end (ch <- value), receive at the other (value := <-ch). The data flows in the direction of the arrow.

Example

The service window between a restaurant's kitchen and its waiters. The cook (one goroutine) places a finished dish on the window; the waiter (another goroutine) picks it up. They never talk directly — the window is the only contact point. Go's motto: "Don't communicate by sharing memory; share memory by communicating." — rather than fighting over shared variables, send the data through a channel.

channel.go — processing an order
package main

import "fmt"

func cook(orders chan string) {
    dish := <-orders               // take an order from the window (waits until one arrives)
    fmt.Println("Cooking", dish)
    orders <- dish + " ready!"     // put the reply back
}

func main() {
    orders := make(chan string)    // channels are created with make()
    go cook(orders)

    orders <- "dosa"               // send the order
    fmt.Println(<-orders)          // wait for the reply and print it
}

dosa ready!

6.4 Race conditions and sync.Mutex

What is a race condition? The mess that happens when two goroutines modify the same variable at the same time. counter++ is really three steps: read → increment → write. Two goroutines both read "100", both compute 101, both write 101 — one increment was lost! Which one wins depends on luck (a race) — hence the name. These bugs appear only occasionally, which makes them the most dangerous kind.

A Mutex (MUTual EXclusion) is a lock. Only one goroutine can hold the lock at a time; the others wait at the door.

Example

A single ATM cabin — while one person is inside, the door is locked. Everyone else queues. Lock() = step in and bolt the door; Unlock() = step out and unbolt it.

mutex.go — a safe counter
package main

import (
    "fmt"
    "sync"
)

func main() {
    var (
        mu      sync.Mutex
        balance = 0
        wg      sync.WaitGroup
    )

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            mu.Lock()           // take the lock
            balance += 10       // now only I am changing this
            mu.Unlock()         // release the lock
        }()
    }
    wg.Wait()
    fmt.Println("Balance:", balance) // always 10000 ✓ (without the mutex it can be less!)
}

The race detector — a tool worth mentioning in interviews

go run -race main.go — Go's built-in race detector catches data races in a running program. "I would run the code with the race detector" is an excellent interview answer.

Deadlock — everyone frozen, waiting on everyone else

Goroutine A says "I'll give only after B gives"; B says "only after A gives" — both are stuck forever. The simplest example: sending on an unbuffered channel when there is no receiver at all:

deadlock.go
func main() {
    ch := make(chan int)
    ch <- 5   // nobody is receiving → main blocks forever
    fmt.Println(<-ch)
}
fatal error: all goroutines are asleep - deadlock!

The good news: when all goroutines are asleep, the Go runtime declares a deadlock and stops the program itself. Ways out: have the receiver ready (in a goroutine), use a buffered channel, always take locks in the same order.

6.5 Worker pool Advanced — read later

The pattern: you have 1000 jobs but want only 3 workers (not one goroutine per job — to avoid overwhelming external systems). Put jobs into a channel; 3 goroutines keep pulling from it with range; results go into a second channel. Reading and understanding it is great; writing it from scratch is not required on Day 4:

workerpool.go
func worker(id int, jobs <-chan int, results chan<- int) {
    for j := range jobs {          // until the jobs channel is drained + closed
        results <- j * 2           // the job: double it
    }
}

func main() {
    jobs := make(chan int, 5)
    results := make(chan int, 5)
    for w := 1; w <= 3; w++ {
        go worker(w, jobs, results) // 3 workers
    }
    for j := 1; j <= 5; j++ { jobs <- j }
    close(jobs)                     // "no more new jobs"
    for i := 0; i < 5; i++ { fmt.Println(<-results) }
}

6.6 context.Context — cancellation and timeouts Advanced — read later

The customer closed their browser — there's no point working on their request anymore. context is the standard way to carry the message "this work is cancelled / finish within this time" down an entire call chain. In backend Go code, nearly every function's first parameter is ctx context.Context. For a beginner interview, this sentence is enough: "Context carries deadlines and cancellation signals across API boundaries; context.WithTimeout gives a context that auto-cancels after a duration, and workers should stop when ctx.Done() is closed."

What is a goroutine and how is it different from a thread?
The Go runtime's featherweight worker — starts at ~2KB, millions can run. OS threads are heavy (MBs); the Go runtime schedules goroutines onto a few threads itself.
A goroutine is a lightweight unit of execution managed by the Go runtime, started with the go keyword. It starts with a tiny stack (~2KB) that grows as needed, so millions can run at once. The runtime multiplexes many goroutines onto a few OS threads, which are far heavier (megabytes of stack, OS-managed scheduling).
What happens to running goroutines when main returns? (The program exits immediately; they are killed.)
What is the difference between buffered and unbuffered channels?
Unbuffered = hand-to-hand — sender and receiver must both be present, blocking until then. Buffered = a tray — the sender doesn't block until it's full.
An unbuffered channel has no capacity: a send blocks until a receiver is ready, so every transfer is a synchronization point. A buffered channel (make(chan T, n)) lets sends proceed until the buffer is full and receives proceed until it's empty. Unbuffered gives you a rendezvous; buffered decouples producer and consumer up to n items.

Concurrency is structuring a program as independently executing tasks — dealing with many things at once. Parallelism is actually executing tasks simultaneously on multiple CPU cores. 7.2 Your first HTTP server — net/http

Go's standard library contains a complete, production-grade HTTP server toolkit — you can build a server without installing anything. (Interview point: many languages require a framework; in Go, net/http is enough.)

server.go — a living server in 15 lines
package main

import (
    "fmt"
    "net/http"
)

func homeHandler(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintln(w, "Welcome to Shiksha Store!")
}

func main() {
    http.HandleFunc("/", homeHandler)
    fmt.Println("Server running on http://localhost:8080")
    http.ListenAndServe(":8080", nil)
}

Run it: go run server.go → open http://localhost:8080 in the browser → you'll see "Welcome to Shiksha Store!". You just wrote a web server. (Stop it with Ctrl+C in the terminal.)

Line-by-line

  1. func homeHandler(w http.ResponseWriter, r *http.Request) — a handler = the function that serves requests for one route (address). The two parameters are always these: r = everything about the incoming request (which URL, which method, what data); w = the pen for writing the response — whatever you write into w reaches the client.
  2. fmt.Fprintln(w, ...) — just like Println, but writes into w (i.e., toward the client) instead of the screen.
  3. http.HandleFunc("/", homeHandler) — routing: "when a request arrives at URL /, run homeHandler." A route = the URL → handler mapping.
  4. http.ListenAndServe(":8080", nil) — starts the server: "sit and listen on port 8080." A port is a number that separates the many servers on one computer — like flat numbers in one building. localhost = "this same computer". This function never returns (the server runs forever) — remember the infinite for loop?

7.3 The Product API — step by step

Now a real, small REST API: it lists products (GET) and adds a new product (POST), in JSON. This is one complete program in a single file — let's go through it piece by piece.

main.go — the Product API (full program)
package main

import (
    "encoding/json"
    "fmt"
    "log"
    "net/http"
    "strconv"
)

// ---- Step 1: the data model ----
// struct tags: `json:"..."` — what to call the field in JSON
type Product struct {
    ID    int     `json:"id"`
    Name  string  `json:"name"`
    Price float64 `json:"price"`
}

// no database yet — an in-memory slice is our store
// (data disappears when the server stops — the database arrives in Part 8)
var products = []Product{
    {ID: 1, Name: "Pen", Price: 10},
    {ID: 2, Name: "Notebook", Price: 45},
}
var nextID = 3

// ---- Step 2: GET /products — all products as JSON ----
func listProducts(w http.ResponseWriter, r *http.Request) {
    w.Header().Set("Content-Type", "application/json")
    json.NewEncoder(w).Encode(products)   // Go slice → JSON → client
}

// ---- Step 3: POST /products — a new product ----
func createProduct(w http.ResponseWriter, r *http.Request) {
    var p Product
    // the client's JSON body → a Go struct (decode)
    if err := json.NewDecoder(r.Body).Decode(&p); err != nil {
        http.Error(w, `{"error":"invalid JSON"}`, http.StatusBadRequest) // 400
        return
    }
    // ---- validation: don't let bad data in ----
    if p.Name == "" || p.Price <= 0 {
        http.Error(w, `{"error":"name required, price must be positive"}`,
            http.StatusBadRequest)
        return
    }
    p.ID = nextID
    nextID++
    products = append(products, p)

    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(http.StatusCreated)     // 201 — "created"
    json.NewEncoder(w).Encode(p)
}

// ---- Step 4: GET /products/{id} — one product ----
func getProduct(w http.ResponseWriter, r *http.Request) {
    id, err := strconv.Atoi(r.PathValue("id")) // the {id} from the URL
    if err != nil {
        http.Error(w, `{"error":"id must be a number"}`, http.StatusBadRequest)
        return
    }
    for _, p := range products {
        if p.ID == id {
            w.Header().Set("Content-Type", "application/json")
            json.NewEncoder(w).Encode(p)
            return
        }
    }
    http.Error(w, `{"error":"product not found"}`, http.StatusNotFound) // 404
}

// ---- Step 5: middleware — a layer every request passes through ----
func logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        log.Println(r.Method, r.URL.Path)  // before: make a note
        next.ServeHTTP(w, r)               // after: hand off to the real handler
    })
}

func main() {
    mux := http.NewServeMux()
    // Go 1.22+: patterns can include the method and {id}
    mux.HandleFunc("GET /products", listProducts)
    mux.HandleFunc("POST /products", createProduct)
    mux.HandleFunc("GET /products/{id}", getProduct)

    fmt.Println("Product API on http://localhost:8080")
    log.Fatal(http.ListenAndServe(":8080", logging(mux)))
}

A request's full journey (the flow) — you must be able to explain this in an interview

  1. The client (curl/browser/app) sends GET /products/2 → it travels the network and arrives at port 8080.
  2. Go's server (ListenAndServe) accepts it and handles it in a new goroutine per request — which is why Go servers take thousands of simultaneous requests. (Part 6 just paid off!)
  3. The request first passes through the middleware (logging) — it gets noted, then moves on.
  4. The mux (router) looks at URL+method and picks the right handler → getProduct.
  5. The handler extracts the id from the path, finds the data, encodes the Go struct to JSON into w, with a status code.
  6. The response travels back over the network → the client reads the JSON. One full cycle.

Middleware — one more look

Middleware is a layer wrapped around a handler — doing something before the request and after the response. Think of a restaurant's doorman: every customer passes by him on the way in — he takes note (logging), checks identity (authentication), and only then lets them through. In the code above, logging() does exactly this: it makes its note, then hands off via next.ServeHTTP. Multiple middleware chain together: logging(auth(mux)).

7.4 Authentication vs authorization + JWT Important if time permits

  • Authentication (AuthN) = "who are you?" — proving identity. The airport ID check. (Logging in = authentication.)
  • Authorization (AuthZ) = "what are you allowed to do?" — permission. An economy boarding pass doesn't open the cockpit. (Only an admin may delete products = authorization.) Tie it to status codes: no identity → 401; identity but no permission → 403.

JWT (JSON Web Token) — the popular login mechanism for APIs: (1) The user logs in with name/password. (2) The server verifies and issues a token — a three-part string (header.payload.signature): the payload carries user info, the signature is signed with the server's secret key. (3) From then on, the client sends the token with every request in the Authorization: Bearer <token> header. (4) The server checks the signature — valid signature = nobody tampered with the token, the user is genuine. The benefit: the server doesn't have to remember each user's session (stateless) — the token is its own proof. Remember: a JWT's payload is not secret (anyone can read it — it's just Base64); it is only tamper-proof.

Database and Testing Basics

The Product API from Part 7 lost its data every time the server stopped. A database fixes that. Alongside it we'll learn how Go code is verified (testing) — both are regular backend interview topics.

8.1 What is a database? Must Learn

What is it? An organized, permanent store of information — a separate running program (such as PostgreSQL, MySQL, or SQLite) that specializes in saving, finding, and protecting data. Our Go server talks to it to store and fetch data.

Example — the familiar world of Excel

Think of a relational database as a super-powered Excel workbook: a table = one sheet (e.g. "products"); a column = a sheet heading (id, name, price) — each column has a fixed data type; a row = one entry (one product's full record). The difference: a database stays fast with millions of rows, serves many users at once, and can enforce rules (price must not be empty!).

  • Primary key (PK) = each row's unique identity — like a roll number. No two rows ever share a PK. Usually the id column.
  • Foreign key (FK) = a reference to another table's PK — it connects tables. E.g., the product_id column in the orders table is an FK to products.id: "which product this order is for."

8.2 SQL — the language of databases Must Learn

SQL (Structured Query Language) is the standard language for instructing a database. Four core actions — CRUD: Create (INSERT), Read (SELECT), Update (UPDATE), Delete (DELETE):

basics.sql
-- creating a table (once)
CREATE TABLE products (
    id    SERIAL PRIMARY KEY,   -- an auto-incrementing unique number
    name  TEXT NOT NULL,        -- may not be empty
    price NUMERIC NOT NULL
);

-- C: a new row
INSERT INTO products (name, price) VALUES ('Pen', 10);

-- R: reading — the king of SQL
SELECT * FROM products;                        -- everything
SELECT name, price FROM products WHERE price > 20;  -- with a condition
SELECT * FROM products ORDER BY price DESC LIMIT 5; -- the 5 priciest

-- U: changing (forget WHERE and *every* row changes — always write WHERE!)
UPDATE products SET price = 12 WHERE id = 1;

-- D: removing
DELETE FROM products WHERE id = 1;

JOIN Important if time permits — reading data from two tables together, via the FK relationship:

join.sql — which customer bought what?
SELECT customers.name, products.name, orders.qty
FROM orders
JOIN customers ON orders.customer_id = customers.id
JOIN products  ON orders.product_id  = products.id;
  • Index Important if time permits — like the index at the back of a book: create an index on a column (CREATE INDEX ... ON products(name)) and searches on that column become direct lookups instead of full-table scans. Trade-off: reads get faster, but every INSERT/UPDATE gets slightly slower (the index must be updated too).
  • Transactions + ACID Important if time permits — an "all or nothing" bundle of steps. A bank transfer: subtract from account A + add to account B — what if power fails in between? A transaction guarantees the half-done state can never persist. ACID = Atomicity (all or nothing), Consistency (rules never end up broken), Isolation (concurrent transactions don't disturb each other), Durability (what's committed survives — even a crash).

8.3 SQL injection — the most famous security mistake Must Learn

Suppose you build a query by concatenating strings with user input:

WRONG — never do this!
// the user typed into the name field: ' OR '1'='1
query := "SELECT * FROM users WHERE name = '" + userInput + "'"
// the resulting query: SELECT * FROM users WHERE name = '' OR '1'='1'
// '1'='1' is always true → *every* user's data leaks out! 💥

The user's input became part of the query — they can smuggle in any command they like (steal data, delete whole tables...). This attack is called SQL injection.

The fix — parameterized queries: put placeholders ($1, ?) in the query and pass values separately. The database driver guarantees a value always stays a value and can never become a command:

RIGHT — always like this
row := db.QueryRow("SELECT id, name FROM users WHERE name = $1", userInput)

8.4 Databases from Go — database/sql Important if time permits

Go's standard library has the database/sql package — one uniform interface for all databases. Each database needs a driver (an external package, via go get) that translates this interface into that database's dialect. This is a living example of the interfaces you learned in Part 3: database/sql says "a driver must look like this", and any driver providing those methods just works!

db.go — connecting the Product API to a database (PostgreSQL)
package main

import (
    "database/sql"
    "fmt"
    "log"

    _ "github.com/jackc/pgx/v5/stdlib" // driver: imported only to register itself
)                                      // _ = a nameless import (side effect only)

type Product struct {
    ID    int
    Name  string
    Price float64
}

func main() {
    // 1) open the connection (the connection string is the DB's address + credentials)
    db, err := sql.Open("pgx", "postgres://user:pass@localhost:5432/shop")
    if err != nil { log.Fatal(err) }
    defer db.Close()                    // close on the way out — remember defer!

    // 2) INSERT — parameterized ($1, $2) — injection-proof
    _, err = db.Exec("INSERT INTO products (name, price) VALUES ($1, $2)",
        "Pen", 10.0)
    if err != nil { log.Fatal(err) }

    // 3) reading several rows
    rows, err := db.Query("SELECT id, name, price FROM products")
    if err != nil { log.Fatal(err) }
    defer rows.Close()

    for rows.Next() {                   // advance row by row
        var p Product
        // Scan: the row's columns → the struct's fields (same order!)
        if err := rows.Scan(&p.ID, &p.Name, &p.Price); err != nil {
            log.Fatal(err)
        }
        fmt.Println(p.ID, p.Name, p.Price)
    }
}

Three pairs to remember: Exec = statements with no result rows (INSERT/UPDATE/DELETE); Query = many rows; QueryRow = one row. And you now know why Scan takes & — pointers!

8.5 Testing — automatic verification of your code Must Learn

A unit test is code that checks one small piece (a function) in isolation — "given this input, exactly this output must come back." An integration test checks that several pieces work together (e.g., the API with a real database). Instead of checking by hand over and over — write the test once, run it a thousand times; if a change breaks something old, it's caught instantly.

Testing is built into Go: files ending in _test.go, functions starting with Test, and the go test command:

bill.go — a function worth testing
package bill

func TotalWithGST(amount float64) float64 {
    return amount * 1.18
}
bill_test.go — the Go signature style: a table-driven test
package bill

import "testing"

func TestTotalWithGST(t *testing.T) {
    // the "table": each row = one case (a slice of anonymous structs)
    tests := []struct {
        name   string
        amount float64
        want   float64
    }{
        {"normal bill", 100, 118},
        {"zero amount", 0, 0},
        {"big bill", 1000, 1180},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {   // each case as a subtest
            got := TotalWithGST(tt.amount)
            if got != tt.want {
                t.Errorf("TotalWithGST(%v) = %v, want %v",
                    tt.amount, got, tt.want)
            }
        })
    }
}

Section A — Foundational Programming (30 questions)

A1. What is a computer program?
A recipe-like, ordered list of instructions.
A set of step-by-step instructions written in a programming language that tells a computer what to do — typically reading input, processing it, and producing output.
What's the difference between a program and a process? (A process is a program while it is running.)
A2. What is source code?
The code a programmer writes in a text file — human-readable.
The human-readable text of a program, written in a programming language and stored in plain files — like .go files. It must be compiled (or interpreted) before the machine can execute it.
What does the compiler turn source code into? (Machine code / an executable binary.)
A3. What is the difference between a compiler and an interpreter?
Compiler = translating the whole book in advance; interpreter = a live translator, line by line.
A compiler translates all source code to machine code ahead of time, producing a fast standalone executable; an interpreter translates and runs code line by line at runtime. Go compiles; Python typically interprets.
Which errors can a compiler catch before the program runs? (Syntax and type errors.)
A4. Why are compiled programs generally faster?
The translation already happened — at run time there's only running left to do.
Because translation happens once, before execution, the CPU runs native machine code directly with no per-line translation overhead, and the compiler can optimize the whole program ahead of time.
Name a cost of compilation. (A separate build step; recompiling after each change.)
A5. What is static typing vs dynamic typing?
Static = each variable's type is fixed and checked at compile time (Go); dynamic = decided while running.
In static typing, every variable's type is known and checked at compile time, catching type errors before the program runs — Go works this way. In dynamic typing, types are attached to values at runtime, so type errors appear only when that line executes.
Does := make Go dynamic? (No — the type is inferred once and fixed at compile time.)
A6. What is the difference between a syntax error and a logic error?
Syntax = broken grammar, the program won't even build; logic = the program runs but the answer is wrong.
A syntax error breaks the language's grammar, so the compiler rejects the program. A logic error compiles and runs but produces wrong results — like adding tax instead of subtracting. Logic errors are harder to find because nothing visibly fails.
What's a runtime error? (An error that occurs during execution — e.g., dividing by zero, index out of range.)
A7. What is an algorithm?
Precise, ordered steps for solving a problem — a recipe without a language.
A precise, step-by-step procedure for solving a problem, independent of any programming language. You design the algorithm first, then express it in code.
What makes one algorithm better than another? (Fewer steps / less memory for the same result — efficiency.)
A8. What is a flowchart?
A picture of an algorithm — boxes (actions), diamonds (decisions), arrows (order).
A diagram of an algorithm's steps: rectangles for actions, diamonds for decisions, arrows for flow. It helps visualize logic before writing code.
Which flowchart shape maps to an if statement? (The diamond/decision.)
A9. What is a variable?
A named box in memory — holds a value, can be changed.
A named storage location in memory that holds a value which can be read and changed during execution. In Go, each variable also has a fixed type.
What is variable scope?
A10. What is a data type?
A declaration of what kind of data a box will hold — number, text, true/false.
A classification that tells the compiler what kind of value a variable holds — integer, floating-point, string, boolean — which determines what operations are allowed and how much memory it uses.
Why can't you add a string and an int directly in Go? (No implicit conversion — types must match.)
A11. What is a constant?
A value that never changes — a GST rate, π.
A named value fixed at compile time that cannot be changed while the program runs. Declared with const in Go. It prevents accidental modification and documents intent.
Can a Go const be computed from a function call? (No — consts must be compile-time values.)
A12. What is an operator?
A symbol that acts on values — +, -, ==, &&.
A symbol that performs an operation on values: arithmetic (+, -, *, /, %), comparison (==, !=, <, >), and logical (&&, ||, !). Comparisons always produce a boolean.
What does % do and name one use. (Remainder; even/odd checks.)
A13. What is a loop and why do we need it?
Doing one task repeatedly — not 500 lines to print 500 marks, just one loop.
A construct that repeats a block of code while a condition holds, so repetitive work is written once. Go has a single loop keyword, for, covering all loop styles.
What is an off-by-one error? (Looping one time too many or too few — e.g., < vs <=.)
A14. What is an infinite loop?
A condition that never becomes false — the program never stops. Servers use them deliberately.
A loop whose condition never becomes false, so it never ends. Usually a bug, but servers intentionally use infinite loops to keep waiting for requests, exiting with break or shutdown signals.
How do you write an intentional infinite loop in Go? (for { }.)
A15. What is a function and what are its benefits?
A named block of code — write once, use everywhere; big programs split into small pieces.
A named, reusable block of code that can take parameters and return values. Benefits: no code duplication, easier testing, clearer structure, and single-place fixes.
What is the difference between defining and calling a function?
A16. Parameter vs argument?
Parameter = the slot written in the function's definition (amount); argument = the actual value passed when calling (500).
A parameter is the variable named in the function definition; an argument is the actual value passed when calling it. In addGST(500), amount is the parameter and 500 is the argument.
What happens to arguments in Go — copy or reference? (They are copied — pass by value.)
A17. What is a return value?
The function's result — sent back out.
The value a function sends back to its caller with the return statement. Go functions can return multiple values, commonly a result paired with an error.
How do you ignore one of two return values in Go? (The blank identifier _.)
A18. What is scope?
The region where a variable is "visible" — inside a block/function doesn't show outside.
The region of code where a name is visible. In Go, a variable declared inside a block or function is visible only there; package-level names are visible across the package, and exported ones beyond it.
What is variable shadowing? (An inner declaration with the same name hiding an outer one — a common := bug.)
A19. What is an array (as a general concept)?
An ordered list of same-type values — each with an index.
An ordered collection of same-type elements stored contiguously, each accessible by an index. Indexing starts at 0 in most languages, including Go.
Why is array access by index fast? (The address is computed directly from the index — no searching.)
A20. Why do indexes start at 0?
An index is "how far from the start" (an offset) — the first element is zero away.
The index represents the offset from the start of the array. The first element is zero elements away, so its index is 0. This convention makes address calculation direct.
What is the index of the last element of an n-element array? (n−1.)
A21. What is a string?
A sequence of characters — text. In Go, an immutable sequence of bytes.
A sequence of characters representing text. In Go specifically, a string is an immutable sequence of bytes, usually UTF-8 encoded text.
Can you change one character of a Go string in place? (No — strings are immutable; build a new one via []rune/[]byte.)
A22. What is a boolean and where is it used?
Only true/false — the result of every if condition, loop condition, and comparison.
A type with exactly two values, true and false. Every condition — in if statements, loops, and comparisons — evaluates to a boolean.
What is the zero value of bool in Go? (false.)
A23. What is a bug? What is debugging?
Bug = a mistake in the code; debugging = finding and fixing it — by printing, using tools, thinking step by step.
A bug is a flaw that makes a program behave incorrectly. Debugging is locating and fixing it — by reading error messages, printing intermediate values, writing tests, or stepping through code with a debugger.
What's the first thing to read when a Go program panics? (The panic message and stack trace — it names the exact line.)
A24. What is an IDE / code editor?
A smart tool for writing code — underlines errors, offers auto-complete. We use VS Code.
A tool for writing code with conveniences like syntax highlighting, autocompletion, inline error checking, and integrated terminals. VS Code with the Go extension is a common Go setup.
What does the Go language server (gopls) provide? (Completion, errors, navigation inside the editor.)
A25. What is a terminal and a command?
Talking to the computer by typing — type a command, press Enter, see the result. E.g. go run main.go.
A terminal is a text interface to the operating system; a command is a typed instruction it executes — like go run main.go. Developers use terminals daily to build, run, and test programs.
What does cd do? (Changes the current directory.)
A26. What is memory (RAM) from a programmer's view?
The running program's temporary workspace — variables live here; every location has an address; wiped when power goes.
RAM is the fast, temporary workspace where a running program keeps its variables and data. Every location has an address — which is what pointers store. It's wiped when the program ends, which is why durable data goes to files or databases.
What's the difference between memory and disk storage? (Speed and volatility — RAM is fast but temporary.)
A27. What do input and output mean?
Input = data the program receives (keyboard, file, network); output = its result (screen, file, response).
Input is data a program receives — keyboard entry, file contents, or network requests. Output is what it produces — printed text, files, or HTTP responses. Most programs are input → processing → output pipelines.
What are stdin and stdout? (The standard input/output streams of a terminal program.)
A28. What is a library / package?
A collection of ready-made code — so you don't rewrite it. Go's standard library has fmt, net/http, testing...
Reusable code written by others that your program imports instead of rewriting — like Go's fmt for printing or net/http for web servers. Go's standard library is famously broad, so many programs need no external dependencies.
How do you add an external package to a Go project? (go get, recorded in go.mod.)
A29. What is version control (Git), briefly?
A tool that keeps the history of code changes — who changed what and when; you can go back; teams can collaborate.
A system that records every change to the code with history — who changed what and when — enabling rollback and team collaboration. Git is the standard tool; code is saved in commits and shared through repositories.
What is a commit? (A saved snapshot of changes with a message.)
A30. What is pseudocode?
Algorithm steps written in plain words — no syntax worries. Saying "let me sketch the approach first" is a good interview habit.
An informal, language-neutral way of writing an algorithm's steps in plain words before coding. In interviews, sketching pseudocode first shows structured thinking and catches logic issues early.
Interviewer: "Walk me through your approach before coding." — pseudocode is exactly how you answer that.

Section B — Go Language (40 questions)

B1. What is Go and why was it created?
An open-source, compiled, statically typed language built at Google in 2009 — simplicity + speed + easy concurrency for large systems.
Go is an open-source, compiled, statically typed language designed at Google (released 2009) by Robert Griesemer, Rob Pike, and Ken Thompson. It was created for large-scale software: fast compilation, simple syntax, built-in concurrency (goroutines/channels), garbage collection, and a strong standard library.
Name three domains where Go is popular. (Cloud/backend services, DevOps tools like Docker and Kubernetes, CLIs.)
B2. What are Go's key features?
Simple syntax (~25 keywords), fast compiles, static types + inference, GC, goroutines/channels, single binary, gofmt, a strong stdlib.
Simplicity (only ~25 keywords), fast compilation to a single static binary, static typing with inference, garbage collection, first-class concurrency via goroutines and channels, a rich standard library, and built-in tooling — gofmt, go test, go vet, race detector.
What is NOT in Go by design? (Classes/inheritance, exceptions for normal errors — and it keeps features minimal deliberately.)
B3. What is a Go module?
The project + its dependencies, identified by the go.mod file. Created with go mod init.
A module is a versioned unit of Go code defined by a go.mod file, which records the module path, Go version, and dependencies. go mod init creates it; go get adds dependencies; go mod tidy cleans them up.
What does go.sum contain? (Checksums that verify dependency integrity.)
B4. Difference between go run, go build, and go install?
run = compile + execute (no file); build = make an executable; install = build and put it in the bin folder.
go run compiles and executes immediately without keeping a binary. go build produces an executable in the current directory. go install builds and places the binary in $GOPATH/bin so it's on your PATH.
Can a Go binary built on Windows run on Linux? (Not directly, but Go cross-compiles easily: GOOS=linux go build.)
B5. Why does Go refuse to compile unused variables and imports?
To keep dead code out — a design decision. Unused variable/import = an error, not a warning.
It's a deliberate design decision: unused code is clutter that hides bugs and slows builds, so Go makes it a compile error rather than a warning. Editors remove unused imports automatically; the blank identifier _ is the explicit escape hatch.
How do you import a package only for its side effects? (import _ "package" — e.g., database drivers.)
B6. What is type inference in Go?
With := or var x = 5 you skip writing the type — Go deduces it from the right side. The type is then fixed.
The compiler deduces a variable's type from its initializer — price := 99.5 is float64 without writing the type. The variable is still statically typed; the type just doesn't need spelling out.
What type does x := 5 get? (int — the default for untyped integer constants.)
B7. What is iota?
An auto-counter inside a const block — 0,1,2... — for building enum-like lists.
iota is a counter inside a const block that starts at 0 and increments per line, used to define enumerated constants: const (Pending = iota; Paid; Shipped) gives 0, 1, 2.
What happens to iota in a new const block? (It resets to 0.)
B8. What are Go's main integer and float types?
int/int8/16/32/64, uint..., float32/float64. For everyday work use int and float64.
Signed ints (int, int8–int64), unsigned (uint, uint8–uint64), and floats (float32, float64). Default choices are int (platform-sized, usually 64-bit) and float64. byte is an alias for uint8 and rune for int32.
Why prefer int over int32 for counters? (It's the natural word size and what the standard library expects, e.g. len returns int.)
B9. How does type conversion work in Go?
Always explicit: float64(x), int(f) (decimals truncated). Go never converts automatically.
Always explicit, written like a function call: float64(qty), int(price) — the latter truncates. Go has no implicit numeric conversions, even between int and int64, which prevents silent precision bugs.
How do you convert between string and int? (strconv.Itoa and strconv.Atoi — not string(n).)
B10. What does string(65) return and why is it a trap?
Not "65" — it's 'A' (the character at code point 65)! For number→string use strconv.Itoa.
It returns "A", because converting an integer to string interprets it as a Unicode code point, not digits. To get "65", use strconv.Itoa(65). A classic beginner trap.
What does strconv.Atoi("abc") return? (0 and a non-nil error — always check it.)
B11. Array vs slice — the core difference?
Array = rigid length, part of the type, copied; slice = a flexible window over an array (pointer+len+cap), grows with append.
Arrays have a fixed length baked into their type and are copied on assignment. Slices are dynamic views over an underlying array — a header of pointer, length, and capacity — growable with append. Day-to-day Go code uses slices almost exclusively.
Is [3]int assignable to [4]int? (No — different types entirely.)
B12. Explain len and cap of a slice.
len = current elements; cap = total room in the underlying array (from the slice's start). When cap runs out, append allocates a bigger array.
len is the number of elements currently in the slice; cap is the size of the underlying array from the slice's start. When append exceeds capacity, Go allocates a bigger array (roughly doubling) and copies elements over.
Why must you write s = append(s, x)? (Append may return a new slice header pointing to a new array.)
B13. What does s[2:5] give you?
Indexes 2, 3, 4 — the end index 5 is not included. And it's not a copy — it's a window onto the same array!
A slice of elements at indexes 2, 3, and 4 — the end index is exclusive. Importantly, it shares the same underlying array, so modifying the sub-slice can modify the original.
How do you make a true independent copy? (Allocate and use the built-in copy(dst, src).)
B14. What is a nil slice and is it usable?
The zero value — pointing at no array. Yet len=0 ✓, range ✓, append ✓ — perfectly usable!
A declared-but-uninitialized slice is nil: it has no underlying array, length 0. It's still safe to use with len, range, and append — appending to a nil slice allocates and works. Only indexing into it panics.
Difference between nil slice and empty slice []int{}? (Both len 0; one is nil, the other points to a zero-length array — behave the same in practice, differ in == nil and JSON output: null vs [].)
B15. How do you create and use a map?
make(map[string]int) or a literal. Set m[k]=v, get v:=m[k], remove delete(m,k), existence check with comma ok.
Create with make(map[K]V) or a literal. Assign with m[key] = value, read with v := m[key], delete with delete(m, key), and check existence with the two-value form v, ok := m[key].
What types can be map keys? (Comparable types — not slices, maps, or functions.)
B16. What happens when you read/write a nil map?
Reading is safe (zero value comes back); writing = panic! Call make first.
Reading from a nil map is safe and returns the zero value; writing to one panics with "assignment to entry in nil map". Always initialize with make or a literal before writing.
Why is map iteration order random? (Deliberately randomized so code never depends on order.)
B17. How do you iterate over a map / slice / string with range?
Slice: index+value; map: key+value (random order); string: byte-index + rune.
for i, v := range slice gives index and element; for k, v := range m gives key and value in random order; for i, r := range str decodes runes, giving byte offset and rune. Unneeded parts are dropped with _ or omitted.
Does range copy the element? (Yes — v is a copy; modify via index s[i].)
B18. Why is a Go string immutable and what are the implications?
Strings can't be modified — safety + cheap sharing. To change one, convert to []byte/[]rune and build a new string.
Strings are read-only byte sequences; you cannot assign to s[0]. This makes strings cheap to share between goroutines and safe as map keys. To "modify", convert to []byte or []rune, edit, and convert back — which copies.
What's the efficient way to build a string in a loop? (strings.Builder, not += concatenation.)
B19. byte vs rune?
byte = uint8, one octet; rune = int32, one whole Unicode character. 'ભ' = 3 bytes but 1 rune.
byte (alias of uint8) is one unit of raw data; rune (alias of int32) is one Unicode code point. ASCII characters fit in one byte, but characters like 'ભ' need multiple bytes in UTF-8 while remaining a single rune.
What does len() count on a string? (Bytes.)
B20. What are Go's for-loop forms?
Four: classic three-part; condition-only (while); bare (infinite); range.
Four shapes of the single for keyword: the classic for i := 0; i < n; i++, condition-only for x > 0 (a while), bare for {} (infinite, exited with break), and for ... := range collection.
What do break and continue do? (Exit the loop entirely / skip to the next iteration.)
B21. What's special about Go's switch?
Auto-break (fallthrough must be requested), multiple values per case, expressionless switch = a clean if/else-if, and type switch too.
Cases break automatically with no fallthrough unless requested; a case can list multiple values; an expressionless switch works as a cleaner if/else chain; and switch v := x.(type) switches on an interface's dynamic type.
When would you actually use fallthrough? (Rarely — cumulative ranges; usually better written another way.)
B22. What are variadic functions?
A function taking any number of arguments — func sum(nums ...int). Inside, nums is a slice. fmt.Println is one!
Functions accepting any number of trailing arguments: func sum(nums ...int) int — inside, nums is a slice. Call with individual values or expand a slice with sum(s...). fmt.Println is variadic.
Can the variadic parameter be anywhere? (Only last.)
B23. What are anonymous functions and closures?
A function without a name — stored in a variable, run immediately, or launched as a goroutine. A closure "captures" surrounding variables.
Functions are values in Go: you can define one without a name, assign it, pass it, or run it inline — common with goroutines and defer. A closure is an anonymous function that captures variables from its surrounding scope and can keep using them after the scope ends.
Classic trap: what did closures in a loop capture before Go 1.22? (The single shared loop variable — now each iteration gets a fresh one.)
B24. What are named return values?
Return values can be named — func f() (total float64, err error); a bare return returns them all. Use only in short functions.
You can name return values in the signature; they act as zero-initialized variables, and a bare return returns their current values. Useful for documentation and defer-based error handling, but bare returns hurt readability in long functions.
Where do named returns shine? (Modifying a return value inside a deferred function.)
B25. Explain defer, its order, and argument evaluation.
Runs at the function's end; multiple defers in LIFO order; arguments evaluated right at the defer line.
defer runs a call when the surrounding function returns — even via panic. Multiple defers run last-in-first-out, and arguments are evaluated at the defer statement, not at exit. Idiomatic for cleanup: defer file.Close() right after opening.
Output of i := 1; defer fmt.Println(i); i = 2? (1.)
B26. What is the error type in Go, really?
A built-in interface: any type with an Error() string method can be an error.
error is just a built-in interface with one method: Error() string. Any type implementing it is an error, which is why custom error types are easy — and why errors are ordinary values you can store, compare, and wrap.
How do you create a quick error? (errors.New or fmt.Errorf.)
B27. errors.New vs fmt.Errorf — and what is %w?
New = a plain message; Errorf = mixes in values; %w = wraps an older error inside — later recognizable with errors.Is.
errors.New makes a fixed-message error; fmt.Errorf formats one with values. With the %w verb, Errorf wraps an underlying error, preserving it so callers can inspect the chain with errors.Is and errors.As while adding context.
Why add context when returning errors up the stack? (So the final message explains where and why: "load product 5: connection refused".)
B28. panic vs error — when which?
Expected failures = return an error; impossible states / programmer bugs = panic. Panic is nearly forbidden in libraries.
Return errors for expected failures — bad input, missing files, network issues. Reserve panic for unrecoverable conditions or impossible states. HTTP servers recover from panics in middleware so one request can't kill the process.
Does panic run deferred functions? (Yes, as the stack unwinds — that's where recover works.)
B29. How does recover work and where must it be called?
It catches a panic — but only when called inside a deferred function. Elsewhere it returns nil.
recover() stops an in-progress panic and returns its value, but only when called directly inside a deferred function; elsewhere it returns nil. Typical pattern: defer func() { if r := recover(); r != nil { ... } }().
After recover, does the panicking function resume? (No — it returns normally from the deferred point; only the caller continues.)
B30. How does Go decide what is public or private?
The first letter: capital = exported (visible outside); lowercase = unexported (package only).
Identifier case: names starting with an uppercase letter are exported from the package; lowercase names are package-private. This applies to functions, types, struct fields, methods, and constants alike — no keywords needed.
Why do JSON-encoded struct fields have to be exported? (encoding/json lives outside your package and can only see exported fields.)
B31. What is a struct and its zero value?
A bundle of fields — your own custom type. Zero value = every field at its own zero value — a "blank form".
A struct is a composite type grouping named fields: type Employee struct { Name string; Salary float64 }. Its zero value is a struct with every field at its own zero value — immediately usable, no constructor needed.
Can structs be compared with ==? (Yes, if all fields are comparable.)
B32. What is struct embedding?
Placing one struct inside another without a field name — its fields/methods "rise up". Go's alternative to inheritance: composition.
Placing a type inside a struct without a field name: type Manager struct { Employee; Team string }. The embedded type's fields and methods are promoted — m.Name works directly. It's Go's composition-based answer to inheritance: reuse without class hierarchies.
Is embedding inheritance? (No — there's no polymorphic base-class behavior; it's composition with promotion.)
B33. Value receiver vs pointer receiver?
Value = a copy (for reading); pointer = the address (for modifying / large structs). If one method needs a pointer, give them all pointers.
A value receiver gets a copy — fine for small, read-only methods. A pointer receiver gets the original — required to mutate the receiver and preferred for large structs. Keep receiver types consistent across a type's method set.
Which method set does an interface see for a value vs a pointer? (Pointer has both; value only value-receiver methods — an advanced follow-up.)
B34. How do interfaces work in Go?
A list of methods; provide those methods and the type satisfies the interface automatically (implicitly) — no "implements" keyword.
An interface declares a method set; any type providing those methods satisfies it implicitly — no declaration. Code then accepts the interface and works with any satisfying type. Famous examples: error, io.Reader, io.Writer.
What's the idiom "accept interfaces, return structs"? (Take interfaces as parameters for flexibility; return concrete types for clarity.)
B35. What is the empty interface (any)?
An interface with no methods — every type satisfies it = "any value at all". Overuse throws away type safety.
any (alias for interface{}) has no methods, so every type satisfies it — it means "a value of any type". Useful for truly generic containers like fmt's arguments, but overuse discards compile-time safety; since Go 1.18, generics are often the better tool.
How do you get the concrete value back out? (Type assertion or type switch.)
B36. Type assertion vs type switch?
Assertion = guessing one type — without comma ok it panics when wrong; type switch = safe branching over several types.
A type assertion extracts a concrete type from an interface: s, ok := v.(string) — always use the comma-ok form to avoid panics. A type switch branches over multiple possible types: switch x := v.(type).
What does v.(string) do if v holds an int? (Without ok — panic; with ok — "", false.)
B37. What are generics in Go?
Go 1.18+: type parameters [T constraint] — one function for many types, with type safety.
Since Go 1.18, functions and types can take type parameters with constraints: func Sum[T int | float64](v []T) T. They eliminate duplicating code per type or falling back to any, keeping full compile-time safety.
What does the constraint comparable allow? (Types usable with == — e.g., map keys.)
B38. What is garbage collection and does Go have it?
Yes — unused memory is reclaimed automatically; no manual free() (unlike C).
Yes — Go has an automatic garbage collector that reclaims memory no longer referenced, so there's no manual free(). Go's GC is a concurrent, low-latency collector designed to keep pause times very small, which suits servers.
Where might a value "escape" to? (The heap — when the compiler's escape analysis finds it outlives its function.)
B39. What does gofmt do and why does it matter?
Formats code into the single official style — all Go code in the world looks alike; zero style arguments.
gofmt rewrites code into the single canonical Go style — tabs, brace placement, spacing. Because all Go code looks the same, reviews focus on logic, and tools can rewrite code safely. It runs on save in most editors.
What else does go vet catch that gofmt doesn't? (Suspicious logic — wrong Printf verbs, unreachable code, copied locks.)
B40. Is Go object-oriented?
No classes/inheritance; but types + methods + interfaces + embedding achieve OOP's goals (encapsulation, polymorphism) — through composition.
Go is not class-based: there's no inheritance or class hierarchy. But it achieves OO goals its own way — methods on any named type, encapsulation via exported/unexported names, polymorphism via interfaces, and reuse via composition and embedding. The mantra: composition over inheritance.
How would you model "a Manager is an Employee" in Go? (Embed Employee in Manager.)

Section C — Pointers, Structs, Interfaces, Errors (15 questions)

C1. What is a pointer and what do & and * mean?
A pointer is a variable holding an address. &x = x's address; *p = the value at p's address.
A pointer holds the memory address of another value. &x takes x's address; *p dereferences a pointer to read or write the value at that address. *int is the type "pointer to int".
What's the zero value of a pointer? (nil.)
C2. Why would you pass a pointer to a function?
(1) So the function can change the original value; (2) to avoid copying a large struct.
Two reasons: to let the function modify the caller's value — since Go always passes copies — and to avoid copying large structs. For small read-only data, plain values are fine and often clearer.
Do you need a pointer to modify a map inside a function? (No — the map header already references shared data.)
C3. What happens when you dereference a nil pointer?
A runtime panic — "invalid memory address or nil pointer dereference". Check for nil first.
A runtime panic. Guard with if p != nil before use, and design APIs so callers know when nil is possible — for example a not-found lookup returning (nil, error).
Does Go have pointer arithmetic? (No — a deliberate safety choice.)
C4. new(T) vs &T{}?
Both give a pointer to a T. new(T) = the zero value; &T{...} = with fields filled — used more in practice.
Both return a *T. new(T) allocates a zeroed T; the composite literal &T{Name: "Ravi"} allocates and initializes in one step, which is why it's the idiomatic choice.
And make()? (Only for slices, maps, channels — returns an initialized value, not a pointer.)
C5. If Go is pass-by-value, why can functions modify slice elements?
The slice header is copied, but the copied header points at the same underlying array — the elements are shared.
The slice header (pointer, len, cap) is copied, but the copied pointer still targets the same underlying array, so element writes are visible to the caller. However, an append that grows the slice inside the function won't be seen by the caller — the function got its own header.
How would the caller see an append too? (Return the slice, or pass *[]T.)
C6. What are struct tags and where are they used?
Little "notes" in backticks after a field — `json:"price"` — instructions about the field for other packages (json, db).
String metadata attached to struct fields, read via reflection by packages like encoding/json: Price float64 `json:"price,omitempty"` controls the JSON key and omits zero values. Also used by database and validation libraries.
What does json:"-" do? (Excludes the field from JSON entirely — e.g., passwords.)
C7. How do you check at compile time that a type satisfies an interface?
One line: var _ Payer = UPI{} — if it doesn't satisfy, compilation fails.
With a blank assignment: var _ Payer = (*UPI)(nil) or var _ Payer = UPI{}. If the type stops satisfying the interface, compilation fails immediately — a cheap safety net.
When is this useful? (When satisfaction is otherwise only checked where the type is actually used.)
C8. Why are io.Reader and io.Writer such important interfaces?
One-method interfaces — "can be read from / written to" — files, network, memory, HTTP bodies all speak this language; one piece of code works everywhere.
They abstract "something you can read bytes from / write bytes to" with a single method each. Files, network connections, HTTP bodies, buffers, and compressors all implement them, so one function like io.Copy(dst, src) works across all of them. They're the model for small, composable Go interfaces.
Why does Go prefer small interfaces? (Easier to satisfy, maximally reusable — "the bigger the interface, the weaker the abstraction".)
C9. How do you define a custom error type?
Give any struct an Error() string method — done, it's an error. It can carry extra data (a code, a field name).
Implement the error interface: type NotFoundError struct { ID int } with func (e *NotFoundError) Error() string. Custom types can carry structured data — IDs, codes — which callers can extract with errors.As.
What is a sentinel error? (A package-level error value like var ErrNotFound = errors.New(...) compared with errors.Is.)
C10. errors.Is vs errors.As?
Is = "does this chain contain that specific error?" (for sentinels); As = "does the chain contain this type of error? If so, extract it."
errors.Is(err, ErrNotFound) reports whether a specific error value appears anywhere in the wrap chain. errors.As(err, &target) finds the first error in the chain matching a type and extracts it. Both exist because errors get wrapped with %w as they travel up.
Why not compare err == ErrNotFound directly? (Wrapping breaks direct equality; Is unwraps.)
C11. What's the difference between a nil interface and an interface holding a nil pointer?
An interface = a (type, value) pair. Pure nil = both empty. Put a nil pointer in, and the type part fills → the interface is non-nil → err != nil is true — a deceptive bug!
An interface value is a (type, value) pair. It equals nil only when both are unset. Storing a typed nil pointer in an interface sets the type part, so the interface is non-nil — which famously makes err != nil true even though the pointer inside is nil. Moral: return a literal nil for errors, never a nil concrete pointer typed as error.
How would you demonstrate this? (func f() error returning a nil *MyError — callers see err != nil.)
C12. Can you add methods to any type?
Only to named types defined in your own package — create type Celsius float64 and add methods to it; not directly to float64.
Methods can be defined on any named type declared in the same package — including ones based on primitives, like type Celsius float64. You cannot attach methods to built-in types or types from other packages directly; you'd wrap them in a new type.
Why must methods live in the same package as the type? (So a type's behavior is defined in one place.)
C13. How does Go achieve polymorphism?
Through interfaces — a function accepting an interface works with every satisfying type. Polymorphism without inheritance.
Through interfaces: a function taking an interface works with every type satisfying it, and the right method is chosen at runtime based on the dynamic type. No inheritance needed — our checkout(p Payer) working for UPI and Card is exactly this.
Static or dynamic dispatch? (Interface method calls are dynamic; direct calls static.)
C14. What does it mean to "wrap" an error and why do it?
Adding context around an old error with %w — "saving order 7: connection refused". The original stays identifiable.
Wrapping adds context while preserving the original: fmt.Errorf("save order %d: %w", id, err). The final message reads like a story of where things failed, and errors.Is/As can still detect the root cause through the chain.
What's a bad error message? ("error occurred" — no operation, no identifiers, no cause.)
C15. Design question: how would you model payment methods (UPI, card, cash) in Go?
One struct per method + one shared interface (a Pay method). Adding a new method = a new struct — old code untouched.
Define a small interface — type Payer interface { Pay(amount float64) (Receipt, error) } — and one struct per method implementing it. Checkout code depends only on Payer, so adding a new payment method means adding a type, not touching existing logic. This is interface-based design and the open/closed principle in idiomatic Go.
How would you unit-test checkout without hitting a real payment gateway? (A fake struct implementing Payer — interfaces make mocking trivial.)

Section D — Concurrency (15 questions)

D1. What is a goroutine?
The Go runtime's lightweight execution worker — started with go f(); ~2KB stack; millions can run.
A lightweight, runtime-managed unit of concurrent execution, started by prefixing a call with go. Goroutines start with ~2KB stacks that grow on demand, and the scheduler multiplexes them onto a small number of OS threads.
How many goroutines does a typical Go HTTP server create? (At least one per request.)
D2. What happens to goroutines when main returns?
The program ends instantly — all goroutines are cut off mid-flight. That's why you must Wait.
The program exits immediately and all goroutines are terminated mid-flight, with no cleanup. That's why you coordinate completion — typically with sync.WaitGroup or channels — before main ends.
Is time.Sleep an acceptable way to wait? (No — it's a race with timing; use WaitGroup.)
D3. Explain sync.WaitGroup.
A counter: Add(n) registers jobs → each goroutine calls Done() at the end → the main goroutine stands at Wait().
A counter for waiting on a set of goroutines: Add(n) before starting them, defer wg.Done() inside each, and wg.Wait() blocks until the counter hits zero. Add must happen before the goroutine starts to avoid a race with Wait.
Why call Add outside the goroutine? (If Add ran inside, Wait might pass before the goroutine even registered.)
D4. What is a channel?
A typed pipe between goroutines — send ch <- v, receive <-ch; the timing coordinates itself (blocking).
A typed conduit for sending values between goroutines: ch <- v sends, <-ch receives. Operations block until the other side is ready (per buffering), which gives you synchronization and communication in one primitive.
Quote Go's concurrency motto. ("Don't communicate by sharing memory; share memory by communicating.")
D5. Buffered vs unbuffered channel?
Unbuffered = hand-to-hand (both present); buffered(n) = a tray of n — the sender blocks once it's full.
Unbuffered: zero capacity, every send waits for a receiver — a rendezvous. Buffered (make(chan T, n)): sends proceed until the buffer is full, receives until it's empty — decoupling producer and consumer up to n items.
When is a buffer of 1 handy? (Non-blocking signal/notification semantics.)
D6. What does closing a channel do? Who should close it?
close(ch) = "no more values coming". Only the sender closes. Sending on a closed channel = panic; receiving = remaining values, then zero values (ok=false). range stops automatically.
close(ch) signals no more values will come. Only the sender should close. Receiving from a closed channel yields remaining values, then zero values with ok == false; for v := range ch exits automatically. Sending on a closed channel panics.
Do you have to close every channel? (No — unclosed channels are garbage-collected; close only to signal completion.)
D7. What is select?
A switch for channels — whichever case becomes ready runs; several ready = random; with default it never blocks; with time.After it's a timeout.
select waits on multiple channel operations and runs whichever becomes ready first (random among ready ones). A default case makes it non-blocking, and pairing with time.After implements timeouts.
Write a 2-second timeout around a channel receive. (select with case <-ch and case <-time.After(2*time.Second).)
D8. What is a race condition? Give an example.
Two goroutines modifying one variable together — counter++ is three steps, so updates get lost; 1000 increments = maybe 937!
When multiple goroutines access the same memory concurrently with at least one write, the outcome depends on timing. Classic example: 1000 goroutines doing counter++ — a read-modify-write — losing updates and ending below 1000.
How do you detect it? (go test -race / go run -race.)
D9. How does sync.Mutex work?
A lock: Lock() admits one goroutine; others wait; Unlock() releases. Wrap it around shared data; use defer for the unlock.
A mutual-exclusion lock: Lock() blocks until the lock is free, guaranteeing only one goroutine runs the critical section; Unlock() releases it. Idiom: mu.Lock(); defer mu.Unlock() so the lock is released on every path.
What is sync.RWMutex for? (Many simultaneous readers, exclusive writers — read-heavy workloads.)
D10. Mutex vs channels — when would you use which?
Simple shared state (counter, cache) = mutex; transferring ownership of data / pipelines / distributing jobs = channels.
Use a mutex to guard simple shared state — counters, maps, caches. Use channels when transferring ownership of data, building pipelines, distributing work, or signaling completion. Rule of thumb: mutex for state, channels for communication.
Can you build a mutex-like lock out of a channel? (Yes — a buffered channel of capacity 1; shows understanding.)
D11. What is a deadlock in Go and when does the runtime detect it?
Everyone stuck waiting on everyone else, forever. If *all* goroutines sleep, the runtime says "fatal error: all goroutines are asleep"; partial deadlocks go undetected.
A state where goroutines wait on each other forever — e.g., sending on a channel no one receives. If every goroutine is blocked, the runtime aborts with "all goroutines are asleep — deadlock!". Partial deadlocks (some goroutines stuck) are not detected and just leak.
Name two prevention strategies. (Consistent lock ordering; receivers ready before sends / buffered channels / timeouts.)
D12. Describe the worker pool pattern.
Put jobs in a channel; a fixed number of workers pull from it with range and process; results go into a second channel. Benefit: control over concurrency.
A fixed number of goroutines (workers) range over a shared jobs channel, process each job, and send results to a results channel; the producer closes the jobs channel when done. It bounds concurrency — useful when each job hits a limited resource like a database.
Why not one goroutine per job? (Unbounded goroutines can overwhelm downstream systems; pools apply backpressure.)
D13. What is context.Context for?
The standard way to carry cancellation + deadlines + request-scoped values down the whole call chain; the first parameter, ctx.
It carries cancellation signals, deadlines, and request-scoped values across API boundaries. Servers pass a ctx into every call; when the client disconnects or a timeout fires, ctx.Done() closes and all downstream work stops early, freeing resources.
How do you give a call a 2-second budget? (ctx, cancel := context.WithTimeout(ctx, 2*time.Second); defer cancel().)
D14. What was the loop-variable capture bug?
Before Go 1.22, one shared loop variable — goroutines all saw its final value. Since 1.22, each iteration gets a fresh variable. A classic trap still asked.
Before Go 1.22, the loop variable was a single variable reused each iteration, so goroutines launched in the loop often all saw its final value. The fix was passing it as a parameter or re-declaring it inside the loop. Since Go 1.22, each iteration gets a fresh variable, but the question remains an interview classic.
How did people fix it pre-1.22? (go func(v T){...}(v) or v := v.)
D15. What does GOMAXPROCS control?
The maximum number of OS threads running Go code at once — default = CPU cores. The ceiling on parallelism.
The maximum number of OS threads executing Go code simultaneously — effectively the parallelism ceiling. It defaults to the number of CPU cores. Concurrency (number of goroutines) can far exceed it; GOMAXPROCS just caps how many run at the same instant.
Does setting GOMAXPROCS=1 remove race conditions? (No — goroutines still interleave; races remain.)

Section E — Backend and HTTP (20 questions)

E1. What is HTTP?
The standard of client-server conversation — a request goes, a response returns; stateless.
HyperText Transfer Protocol — the standard request-response protocol of the web. A client sends a request (method, URL, headers, optional body); the server returns a response (status code, headers, body). Each request is independent — HTTP itself is stateless.
What does HTTPS add? (TLS encryption + server identity verification.)
E2. What are the parts of an HTTP request and response?
Request: method + URL + headers + body. Response: status code + headers + body.
A request has a method (GET/POST/...), a path, headers (metadata like Content-Type, Authorization), and an optional body (e.g., JSON). A response has a status code, headers, and a body. In Go, these map to *http.Request and what you write via http.ResponseWriter.
Where does a JWT travel? (The Authorization header: "Bearer <token>".)
E3. Explain the common HTTP methods.
GET read, POST create, PUT replace entirely, PATCH change a part, DELETE remove.
GET reads a resource, POST creates one, PUT replaces one entirely, PATCH updates part of one, DELETE removes it. REST APIs map these onto resource URLs like /products and /products/{id}.
Which of these are idempotent? (GET, PUT, DELETE — repeating gives the same result; POST is not.)
E4. What is idempotency and why does it matter?
One request sent twice still gives the same outcome. Vital for network retries — POST twice = two orders!
An operation is idempotent if doing it multiple times has the same effect as once. GET, PUT, DELETE are idempotent; POST is not — retrying a POST can create duplicates. It matters because networks retry; payment APIs often add idempotency keys to make POSTs safe.
How do payment APIs make POST safe to retry? (Client-supplied idempotency keys.)
E5. Explain status code groups and the most common codes.
2xx success, 3xx redirect, 4xx client error, 5xx server error. Know 200, 201, 400, 401, 403, 404, 500 by heart!
2xx success (200 OK, 201 Created, 204 No Content), 3xx redirects, 4xx client errors (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found), 5xx server errors (500 Internal Server Error, 503 Unavailable).
Which code for valid JSON that fails business validation? (400 — or 422 by some conventions.)
E6. What is JSON and why is it the default API format?
Key-value data as text — humans can read it, every language can parse it, it's lightweight.
JavaScript Object Notation — a lightweight text format of key-value pairs, arrays, numbers, strings, booleans, and null. It's human-readable, supported by every language, and maps naturally to structs and maps, so it became the default exchange format for REST APIs.
What Go types does a JSON object/array/number decode into by default (into any)? (map[string]any, []any, float64.)
E7. json.Marshal vs json.NewEncoder?
Marshal = struct → []byte (when you need it in hand); Encoder = writes straight into a writer (like w) — the norm in handlers.
json.Marshal returns the JSON as a byte slice — useful when you need it in memory. json.NewEncoder(w).Encode(v) streams directly to an io.Writer like the ResponseWriter — the common choice in handlers. Unmarshal/Decoder mirror this for reading.
Why must encoded struct fields be exported, with tags for naming? (json can only see capitalized fields; tags map them to lowercase keys.)
E8. What is a handler in Go's net/http?
The function serving one route's requests — with the fixed signature (w http.ResponseWriter, r *http.Request).
Anything implementing ServeHTTP(w, r); most code uses plain functions of signature func(w http.ResponseWriter, r *http.Request) registered with HandleFunc. r carries the request; whatever you write to w — headers, status, body — becomes the response.
In what order must you set headers, status, and body? (Headers → WriteHeader(status) → body; after the first write the status is locked at 200.)
E9. What is a ServeMux / router?
The thing that maps URL+method → handler. Go 1.22+ supports patterns like "GET /products/{id}", with PathValue for {id}.
A multiplexer that routes incoming requests to handlers by pattern. Since Go 1.22, the standard ServeMux supports methods and wildcards — mux.HandleFunc("GET /products/{id}", h) with r.PathValue("id") — covering what third-party routers were used for.
What happens when no pattern matches? (404 from the mux.)
E10. How does Go serve many requests at once?
Each request gets its own goroutine — thousands at a time. Consequence: shared state needs a mutex.
The net/http server runs each connection/request in its own goroutine, so handlers execute concurrently by default. That gives huge throughput for free, but any shared mutable state inside handlers must be synchronized.
Make our in-memory product store safe. (Guard the slice/map with a sync.Mutex or RWMutex.)
E11. What is middleware and how is it written in Go?
A layer around a handler — doing work before/after (logging, auth, recover). A function that takes a handler and returns a handler; they chain.
A function that wraps a handler to run logic before/after it: func Logging(next http.Handler) http.Handler. Common middleware: request logging, authentication, panic recovery, CORS, rate limiting. They compose into chains: Logging(Auth(mux)).
Why is panic-recovery middleware important? (One panicking handler would otherwise kill the request — recovery converts it to a 500 and keeps serving.)
E12. Query parameters vs path parameters vs body?
Path = the thing's identity (/products/5); query = filters/options (?sort=price); body = the data being sent (a POST's JSON).
Path parameters identify a resource (/products/5 — r.PathValue). Query parameters filter or modify a read (?minPrice=10&sort=price — r.URL.Query()). The body carries data being submitted, typically JSON on POST/PUT/PATCH.
Where would the page number for a product list go? (A query parameter — ?page=2.)
E13. 401 vs 403?
401 = no/invalid identity (please log in); 403 = identity known but not allowed.
401 Unauthorized means the request lacks valid authentication — the client should log in or fix its credentials. 403 Forbidden means identity is known but permission is denied — logging in again won't help.
Which one for an expired JWT? (401.)
E14. Authentication vs authorization?
AuthN = who you are (the ID check); AuthZ = what you're allowed to do (the boarding-pass class).
Authentication verifies who you are — passwords, tokens, OTPs. Authorization decides what you may do — roles and permissions. They map to 401 and 403 respectively, and middleware usually handles both: first identify, then check permission.
Where in the request does the proof of identity usually travel? (The Authorization header.)
E15. Explain the JWT flow.
Login → the server issues a token (header.payload.signature, signed with a secret) → the client sends it on every request → the server verifies the signature. Stateless; the payload is readable — not secret, only tamper-proof.
On login the server issues a signed token (header.payload.signature). The client sends it on every request in the Authorization header; the server verifies the signature with its secret and trusts the claims inside — no server-side session storage. Note the payload is only Base64-encoded, so it's readable: JWTs guarantee integrity, not secrecy.
What belongs in JWT claims and what never does? (User ID, role, expiry — yes; passwords or secrets — never.)
E16. What is CORS, in one minute?
A browser rule: one site's JS can't call another domain's API — unless the server grants permission via special headers (Access-Control-Allow-Origin).
Cross-Origin Resource Sharing: browsers block JavaScript on one origin from calling APIs on another unless the API's responses include headers like Access-Control-Allow-Origin permitting it. It's a browser-enforced safety rule; server-to-server calls are unaffected. In Go it's typically handled by middleware setting those headers.
Why does the browser sometimes send an OPTIONS request first? (The CORS preflight check.)
E17. How do you return a proper error response from an API?
The right status code + a JSON body: {"error": "product not found"}. Internal details (stack traces, SQL) never reach the client — they go to the logs.
Set the right status code and return a small JSON body like {"error": "product not found"}. Log full internal details server-side, but never leak stack traces or SQL to clients — both for security and for a stable API contract.
Which code when your database is down? (500 — or 503; it's a server-side failure, never 404.)
E18. How would you test an HTTP handler in Go?
The standard library's net/http/httptest — build a fake request, capture the response in a recorder, assert on status/body — no real server needed.
With net/http/httptest: build a request via httptest.NewRequest, a response recorder via httptest.NewRecorder, call the handler directly, and assert on the recorded status and body. No real network or server needed, so tests are fast and deterministic.
And manual testing tools? (curl or Postman against the running server.)
E19. What is request validation and where does it happen?
Checking the client's data before accepting it — empty name? negative price? Bad → 400 + a reason. At the top of the handler, right after decoding.
Checking incoming data before acting on it — required fields present, numbers in range, formats valid. It happens right after decoding the body: reject bad input with 400 and a clear message. Never trust client input; validation is the API's first line of defense alongside parameterized queries.
Why validate server-side even if the frontend already validates? (Clients can bypass the frontend entirely — curl talks straight to the API.)
E20. What is graceful shutdown?
When stopping a server, let in-flight requests finish and take no new ones — server.Shutdown(ctx). No dropped requests during deploys.
Stopping a server without cutting off in-flight requests: stop accepting new connections, let active handlers finish within a timeout, then exit — srv.Shutdown(ctx) in Go, triggered by OS signals. It prevents dropped requests during deploys and restarts.
What signal does Ctrl+C send? (SIGINT — caught via os/signal to trigger Shutdown.)

Section F — Database and Testing (10 questions)

F1. SQL vs NoSQL — one-liner each?
SQL = tables + fixed schema + ACID (PostgreSQL, MySQL); NoSQL = flexible documents/keys, easy scaling (MongoDB, Redis). As a beginner, make SQL solid.
SQL databases store structured data in related tables with a fixed schema and strong ACID guarantees. NoSQL covers flexible models — documents, key-value, wide-column — trading schema rigidity for flexibility and easy horizontal scale. Default to SQL unless the data model demands otherwise.
Name one SQL and one NoSQL database. (PostgreSQL; MongoDB/Redis.)
F2. Write the four CRUD statements for a products table.
INSERT, SELECT, UPDATE (with WHERE!), DELETE (with WHERE!).
INSERT INTO products (name, price) VALUES ('Pen', 10); · SELECT * FROM products WHERE price > 20; · UPDATE products SET price = 12 WHERE id = 1; · DELETE FROM products WHERE id = 1; — and always double-check the WHERE on UPDATE/DELETE.
What happens to UPDATE without WHERE? (Every row changes — a classic production disaster.)
F3. What is a JOIN?
Reading rows from two tables together, connected through their FK — orders + customers + products in one query.
A query operation combining rows from related tables via their key relationship: SELECT c.name, p.name FROM orders o JOIN customers c ON o.customer_id = c.id JOIN products p ON o.product_id = p.id. INNER JOIN keeps matches; LEFT JOIN also keeps unmatched left rows.
When does LEFT JOIN matter? (E.g., customers including those with zero orders.)
F4. What is an index and its trade-off?
A book's back-of-book index — searches get fast; in exchange, writes (INSERT/UPDATE) get slightly slower + extra storage.
A data structure that lets the database find rows by a column without scanning the whole table — making reads dramatically faster. The trade-off: every write must also update the index, and it takes storage. Index the columns you filter and join on.
Is the primary key indexed? (Yes — automatically.)
F5. Explain transactions and ACID.
"All steps or none" — a bank transfer can never stay half-done. ACID: Atomicity, Consistency, Isolation, Durability.
A transaction groups statements so they all commit or all roll back. ACID: Atomicity (all or nothing), Consistency (rules never end up violated), Isolation (concurrent transactions don't see each other's half-done work), Durability (committed data survives crashes). In Go: tx, _ := db.Begin() ... tx.Commit() or tx.Rollback().
Give a case that must be a transaction. (Debit one account + credit another.)
F6. How does Go talk to SQL databases?
database/sql (the standard interface) + one driver per database. Exec / Query / QueryRow + Scan.
Through the standard database/sql package, which defines a driver-agnostic API; a driver package per database (imported with _ for registration) implements it. You use Exec for writes, Query/QueryRow for reads, and Scan to map columns into variables — always with parameterized placeholders.
Why is the driver imported with a blank identifier? (Only its side effect — registering itself — is needed.)
F7. What is connection pooling?
A new DB connection per request is expensive — a pool keeps ready connections that get borrowed and returned. In Go, the *sql.DB from Open IS the pool!
Opening a database connection is expensive, so a pool keeps a set of ready connections that queries borrow and return. In Go, *sql.DB is itself a managed pool — create it once at startup and share it; never open per request.
Is *sql.DB safe for concurrent use? (Yes — by design.)
F8. How are tests structured in Go?
File: xxx_test.go; function: TestXxx(t *testing.T); fail: t.Errorf/Fatalf; run: go test ./...
Tests live beside the code in _test.go files, as functions TestXxx(t *testing.T). Failures are reported with t.Errorf (continue) or t.Fatalf (stop this test). go test ./... runs everything; -v for detail, -run Name for one test, -cover for coverage.
Unit vs integration test? (One function in isolation vs multiple parts together — e.g., API + real database.)
F9. What are table-driven tests?
A table of cases (a struct slice) + one loop — adding a case = adding one row. Go's standard style.
The idiomatic Go pattern: define a slice of test cases (name, input, expected), then loop and run each as a subtest with t.Run. Logic is written once; adding coverage is adding a row. Nearly all standard-library tests use this style.
What does t.Run give you over a plain loop? (Named subtests — run/filter/report individually.)
F10. What do go vet and the race detector add over the compiler?
vet = catches suspicious code that compiles (wrong Printf verbs...); -race = catches data races in running code.
go vet statically finds suspicious-but-compiling code: mismatched Printf verbs, unreachable code, misuse of locks. The race detector (go test -race) instruments the binary to catch real data races at runtime. Both belong in CI alongside gofmt and tests.
Why can't the compiler catch data races? (They depend on runtime interleaving, not syntax.)

        }
    }
    fmt.Println(count)   // 3 (o, a, i)

    // G13 — swap without a temp
    a, b := 5, 9
    a, b = b, a
    fmt.Println(a, b)    // 9 5

    // G14 — two sum: find the index pair whose sum = target
    nums, target := []int{2, 7, 11, 15}, 9
    seen := map[int]int{} // value → index
    for i, v := range nums {
        if j, ok := seen[target-v]; ok {
            fmt.Println(j, i)        // 0 1  (2+7=9)
            break
        }
        seen[v] = i
    }

    // G15 — anagram check
    f := func(s string) map[rune]int {
        m := map[rune]int{}
        for _, r := range s { m[r]++ }
        return m
    }
    m1, m2 := f("listen"), f("silent")
    same := len(m1) == len(m2)
    for k, v := range m1 {
        if m2[k] != v { same = false; break }
    }
    fmt.Println(same)    // true
}

Interview tips: (1) G14's idea — "look up the complement in a map" — reappears in many problems: instead of two brute-force loops (O(n²)), one map pass (O(n)). Describe both to the interviewer and explain why the map wins. (2) In G15, maps can't be compared with == — you must compare them with a loop. (3) Always mention edge cases out loud: empty string? one element? negative numbers?

  1. Go: Open-source, compiled, statically typed language from Google (2009) — simple syntax, fast single-binary builds, garbage collection, built-in concurrency (goroutines/channels), strong standard library. Teams choose it for backend services, cloud tooling (Docker/Kubernetes are Go), and easy-to-maintain codebases. Full marks: three features + one usage domain.
  2. Compiled vs interpreted: a compiler translates everything ahead of time to machine code (fast execution, early error catching); an interpreter translates line-by-line at runtime. Go compiles to a standalone binary via go build. Full marks: a benefit + Go's placement.
  3. Zero values: automatic defaults for uninitialized variables — int 0, string "", bool false, pointer nil, slice nil. No garbage values in Go. Full marks: all five correct.
  4. Array/slice/append: array fixed-length (part of the type), copied; slice = a pointer+len+cap view, growable. Append beyond cap → a new bigger array is allocated, elements copied, a new header returned — hence s = append(s, x). Full marks: the three header parts + the re-allocation + the reason for re-assigning.
  5. Comma ok: v, ok := m[k] — a plain read returns the zero value for missing keys, so you can't distinguish "absent" from "present with zero". Full marks: the zero-value reason stated.
  6. Word count: strings.Fields + map[string]int with counts[w]++ (as in Part 4 Ex16). Full marks: working code + explaining the map zero-value trick.
  7. Pointer demo: the deposit(&balance) example (3.11): the function takes a *float64 and writes through *p. Full marks: the jobs of both & and * stated.
  8. Payment design: type Payer interface { Pay(amount float64) string } + UPI/Card structs with Pay methods; checkout(p Payer). The connection is implicit — no implements keyword; having the methods is enough. Full marks: the word "implicit" + the benefit (new method = new type, old code untouched).
  9. divide: returns (float64, error); b==0 → errors.New("division by zero"); success → result, nil; the caller checks if err != nil first. Full marks: error last + nil on success + immediate check.
  10. WaitGroup: wg.Add(1) in the loop (before the goroutine), defer wg.Done() inside, wg.Wait() at the end. Without it: main exits → goroutines killed → possibly nothing prints. Full marks: Add in the right place + the bug explained.
  11. Race: concurrent access to the same memory with ≥1 write → lost updates (the counter++ example). Prevention: a Mutex, channels; detection: -race. Full marks: definition + two fixes.
  12. Request flow: client → TCP/port → Go server accepts, spawns a goroutine → middleware (logging/auth) → the mux matches GET /products/{id} → handler: PathValue("id") → Atoi → store/db lookup → found: Content-Type JSON + encode struct (200); missing: 404 + a JSON error body → the response returns to the client. Full marks: goroutine-per-request + the mux + the 404 all present.
